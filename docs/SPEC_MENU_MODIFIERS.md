# אפיון: תוספות ושינויים · הערות הכנה · אלרגנים · ארוחות · הגדלות מכירה · סועדים · מנות · עמדות

> מסמך אפיון לפני בנייה. מונחים באנגלית בסוגריים — כפי שהם מופיעים בקוד.
> נכתב אחרי קריאת הקוד הקיים (קופה, שרת, דשבורד) ומחקר על Toast, Square for Restaurants,
> Lightspeed Restaurant (K-Series), Oracle Simphony, טאביט וביקום (§2).
> כל סעיף מסתיים בהחלטה. החלטות שרק הלקוח יכול לקבל מסומנות **[לאישור]** — לכל אחת נבחרה ברירת מחדל ונבנית לפיה.

## 0. תקציר החלטות

| נושא | החלטה |
|------|-------|
| מבנה | **קבוצות תוספות** (Modifier Groups) ברמת ארגון/חברה, משותפות לכמה מוצרים. לכל קבוצה **אפשרויות** (Options) עם תוספת מחיר, אלרגנים, שם למטבח, ברירת מחדל ומוצר מקושר (מלאי/דוחות). |
| שיוך | לקטגוריה **ו**/או למוצר. **מוצר גובר על קטגוריה** (רשימה משלו מחליפה, לא מתווספת); תת־קטגוריה יורשת מההורה; "ללא תוספות" מפורש עוצר ירושה — אותו כלל של מדפסות הבונים. |
| בחירה | min / max לכל קבוצה (min≥1 = חובה), "ראשונות חינם" (freeCount — הזולות ביותר חינם), כמות לאפשרות (×2), מקדימים: **מעט / הרבה / בצד** (הרבה = מחיר כפול). הסרות ("בלי עגבנייה") הן קבוצה מסוג removal. |
| הערות | הערות מוכנות (chips) לפי מוצר/קטגוריה + הערות כלליות לכל המנות, טקסט חופשי, דגל **"חשוב"** שמודפס הפוך (לבן על שחור). |
| אלרגנים | רשימה קבועה: 8 עיקריים + 6 אופציונליים (EU-14). על מוצר ועל אפשרות. בקופה: אייקון/צ׳יפים; הערת "אלרגיה" מתריעה כשהמנה או התוספות מכילות את האלרגן; בבון — מסגרת הפוכה בולטת. |
| ארוחות | מוצר ארוחה עם **משבצות** (Slots: עיקרית / תוספת / שתייה) — לכל משבצת מוצרים מותרים עם תוספת מחיר ("צ׳יפס גדול +3"), ברירת מחדל, חובה/רשות. רכיב שומר על התוספות וההערות שלו. |
| ארוחה בקבלה | **שורה אחת** במחיר הארוחה; הרכיבים ותוספות בתשלום — כשורות משנה מוזחות. |
| ארוחה בדוחות | **הקצאת הכנסה** לרכיבים: תוספות־מחיר ושינויים בתשלום — לרכיב שלהם; מחיר הבסיס — יחסי למחירון הרכיבים; ההנחה — יחסית לברוטו. סכום הרכיבים = שורת הקבלה **בדיוק באגורות** (שיטת השארית הגדולה). "כמה המבורגרים מכרנו" כולל המבורגרים בתוך ארוחות. |
| ארוחה במטבח / מלאי | כל רכיב מנותב לעמדה/מדפסת שלו (המבורגר → גריל, צ׳יפס → טיגון, קולה → בר); מלאי יורד לכל רכיב ולכל אפשרות עם מוצר מקושר. |
| מבצעים והנחות | מבצע/הנחה חלים על **השורה כולה** (בסיס + תוספות). ארוחה היא מוצר — מבצע יכול לחול עליה, לא על רכיביה. "לא מקבל הנחות" של מוצר הארוחה חל על כל השורה. |
| זיכוי | ברמת **שורה** (ארוחה שלמה / מנה עם תוספותיה, כולל כמות חלקית). לא מזכים רכיב בודד מתוך ארוחה. |
| שוברים | שובר הפקה שמכסה מוצר מכסה את **מחיר הבסיס** של המנה; תוספות בתשלום נשארות לתשלום. |
| הגדלות מכירה | כללים: טריגר (מוצר/קטגוריה) → הצעה (הוסף מוצר / שדרג לארוחה / הגדל), טקסט, מחיר מוצג, שעות. **כרטיס לא חוסם** בקופה, נגיעה אחת לקבלה. פרמטר קופה להפעלה. סטטיסטיקה בענן (הוצג/התקבל/נדחה + הכנסה). |
| סועדים | בשולחן בלבד, רשות: "סועד פעיל" (1..N, ניתן לתת שם), שורות חדשות אליו, העברה בין סועדים, עגלה מקובצת, הסועד מודפס בבון. מכין פיצול לפי סועד. |
| מנות (Courses) | רשימת מנות לחברה, ברירת מחדל לקטגוריה/מוצר. בשולחן: "שלח" שולח רק מנות "מוצאות"; מנה בהמתנה מסומנת "בהמתנה"; "הוצא <מנה>" = FIRE. בדלפק — הכול יוצא מיד. |
| עמדות (Stations) | **לא** מערכת ניתוב שנייה: עמדה = יעד ניתוב בעל שם במערכת המדפסות הקיימת (עמדה → מדפסת אחת או יותר לכל סניף); מוצר/קטגוריה משויכים לעמדה; ניתוב ישיר למדפסת (הקיים) ממשיך לעבוד וגובר. |
| סנכרון | כל ההגדרות יורדות בסנכרון הקטלוג (מלא + דלתא) כבלוק `menu` שלם, נשמרות בקופה ועובדות **אופליין**. |
| תאימות | שורה ישנה בלי פרטים = שורה רגילה. קופה ישנה מתעלמת מהבלוק. שרת ישן — הקופה מוכרת כמו היום. |

## 1. מה כבר קיים בקוד

| רכיב | מה יש היום | מה חסר |
|------|-----------|--------|
| הערה לשורה (קופה) | `CartLine.notes` (טקסט חופשי בעריכת שורה בעגלה); בשולחן — `TableExtras.notes` ("עוד ← הערות"); `KitchenDiff` מעדיף את הערת השולחן ומדפיס אותה ממוסגרת מתחת לשורה. | הערות מוכנות, דגל "חשוב", אלרגיות, מבנה (לא רק טקסט). |
| `notes` בשורה שנשמרת | `transaction_items.notes` משמש גם לסימון "כלול בשובר #12" (`VOUCHER_LINE_NOTE_PREFIX`). | פרטי השורה צריכים שדה משלהם — לא לערבב עם סימון השובר. |
| בונים | `KitchenTicket`/`KitchenTicketLine` (מוצר, קטגוריה, שם, כמות, הערות), ניתוב מוצר/קטגוריה → מדפסות (`KitchenRouting`, `kitchen_printer_routes` בענן, מוצר גובר על קטגוריה, ירושה בעץ), תור עמיד, הדפסה דרך הענן/שרת הדפסות. | שורות משנה (תוספות/הסרות/הערות/אלרגיות), סועד, מנה, פירוק ארוחה לעמדות. |
| מבצע "קומבו" | סוג 7 במנוע המבצעים: כשכל רכיבי הקומבו **בסל כמוצרים נפרדים** — מחיר קבוע לחבילה. | קומבו הוא תמחור אוטומטי בדיעבד, לא "ארוחה" שהמלצר בונה עם בחירות. שני הכלים נשארים: **ארוחה** = מוצר שנבנה בבחירה; **קומבו** = מבצע על פריטים נפרדים. |
| "לא מקבל הנחות" | `noDiscount` למוצר, נאכף בקופה (הנחת שורה, הנחת סל, מבצעים). | — (ארוחה היא מוצר — הדגל חל). |
| שובר פריט / שובר הפקה | `ticket_mode` (שובר לכל יחידה/שורה/מכירה, מוצר גובר על קטגוריה); שובר הפקה מכסה שורות לפי מוצר (`coverByVoucher`, לפי `line.total`). | הגדרה מה השובר מכסה כשיש תוספות. |
| זיכוי | ברמת שורה (`refundOfItemId`), לפי מה ששולם בפועל (`RefundMath`). | העברת פרטי השורה לשורת הזיכוי (לדוחות ולמלאי). |
| דוחות | מכירות לפי מוצר (`build_product_sales_report`) — מקובץ לפי `transaction_items`. | פירוק ארוחות, דוח תוספות, דוח ארוחות, דוח הגדלות מכירה. |

## 2. מחקר: איך מערכות מובילות עושות את זה

> מקורות בנספח א׳. איפה שהתיעוד של ספק לא אומר דבר — כתוב כך.

### 2.1 קבוצות תוספות (Modifier Groups)
| מערכת | מה יש |
|-------|-------|
| **Toast** | `ModifierGroup` משותפת: `minSelections`/`maxSelections` (null = ללא הגבלה), `requiredMode` (REQUIRED / OPTIONAL_FORCE_SHOW / OPTIONAL), תמחור: ללא / מחיר אחיד / לכל אפשרות / **Sequence** ("הראשונה חינם, השנייה 1$, השלישית 1.5$" — כך Toast עושה "N חינם") / לפי גודל. `ModifierOption`: `price`, `isDefault`, `allowsDuplicates` (×3 מחויב פי 3), `kitchenName`, `prepStations`, **קבוצות מקוננות**. כל אפשרות נשענת על **פריט** (מלאי ו־86). שיוך ברמת קבוצת תפריט יורש לפריטים; פריט יכול לעקוף. |
| **Square** | `CatalogModifierList`: `min/max_selected_modifiers`, `allow_quantities`, מודיפייר טקסט חופשי, `hidden_from_customer`; `CatalogModifier`: מחיר (גם שלילי), `on_by_default`, `kitchen_name`, קינון עד 3 רמות. עקיפה לפריט (`CatalogItemModifierListInfo`). **אין "N חינם".** |
| **Lightspeed K** | קבוצות min/max (1–99), ברירת מחדל, אפשרויות חינם אלא אם תומחרו בקבוצה; בנפרד — **Production instructions** (הוראות הכנה בלי מחיר ובלי סטטיסטיקה, למשל מידת עשייה). |
| **Oracle Simphony** | "Condiments" בקבוצות; סוגים: **Required** (מידת עשייה), **Allowed**, **Forced** (min/max), **Default** (רכיב שבא עם המנה, מוסתר). "N חינם" דרך **Thresholds** — אחרי N יחידות עוברים לסדרת מחיר אחרת. |
| **טאביט** | קבוצת תוספות: טקסט חופשי **או** פריטי קטלוג — רק תוספת שהיא פריט יכולה לשאת מחיר, להופיע בדוחות ולהיות מוגבלת. min/max בשיוך לפריט. **תוספת יכולה להיות מנותבת לעמדה אחרת** מהמנה. שם ללקוח נפרד. |
| **ביקום** | אין תיעוד פומבי לקבוצות תוספות. |

**Best practice**: קבוצה משותפת עם רשומת שיוך שיכולה לעקוף; אפשרות שנשענת על פריט אמיתי (מלאי, דוחות); טקסט חופשי — מסלול נפרד בלי מחיר; קינון 2–3 רמות לכל היותר.
**אצלנו**: קבוצה משותפת, אפשרות עם `linked_product_id` אופציונלי (מלאי ודוח), "N חינם" כ־`free_count` (הזולות חינם — כמו Toast בקומבו), `allow_quantity`, שם למטבח; שיוך עם ירושה ומוצר גובר. קינון ועקיפת מחיר/מינימום לפריט — שלב 2.

### 2.2 מקדימים (Pre-modifiers): בלי / מעט / הרבה / בצד / תוספת
- **Toast**: קבוצות Pre-modifier: `displayMode` PREFIX ("ADD Bacon") / SUFFIX ("Bacon ON SIDE"), `multiplicationFactor` **או** `fixedPrice` — התיעוד ממליץ 0 ל־NO/LIGHT ו־2 ל־EXTRA.
- **Square**: כפתורי Add / Extra / Side / Sub / No / Allergy — תמחור גס (כל אחד חוץ מ־No מחויב כרגיל), תלונה ותיקה בקהילה.
- **Simphony**: Description (Lite/Extra), **No** (מסיר רכיב ברירת מחדל), **Add**, **Sub**, Plain, Reset, Clear.
- **טאביט**: "placings" — **"עם"** ו**"בצד"** + מותאמים; "רכיבים כלולים" שהאורח מוריד.
- **ביקום**: הוסיפה לאחרונה הערת מנה **"רק"** (גוררים רכיב ל"רק").
- **בבון**: רכיבי ברירת מחדל לא מודפסים אלא אם שונו; Toast מדפיס ברירות מחדל בשחור ושינויים באדום.

**אצלנו**: מקדימים **מעט** (×1) / **הרבה** (×2) / **בצד** (×1) כמאפיין קבוצה (`allowPre`); **"בלי"** = קבוצת הסרות (removal), מודגש בבון; **"תוספת"** = קבוצת addon ("+ גבינה"). הסרת רכיב לא מזכה בכסף. "רק" ו"במקום" — שלב 2.

### 2.3 ארוחות / קומבו
- **Toast**: אין סוג "קומבו" ל־POS. הדרך המתועדת — פריט "ארוחה" עם קבוצות חובה (עיקרית / תוספת / שתייה, 1/1) ו**upcharges**; הרכיבים מודפסים כמודיפיירים. חלופה — הנחת קומבו אוטומטית שמחלקת את מחיר הקומבו **יחסית** בין הפריטים, וכשיש הגבלת תוספות — חלה על **הזולות**.
- **Square** (Combo, אוקטובר 2025): משבצות עם "מספר בחירות", ±upcharge לפריט, ברירת מחדל; **כל רכיב לעמדה שלו** עם תג "חלק מ־Burger Combo"; מלאי לכל רכיב; **דוח Item Sales מציג רכיבים**.
- **Lightspeed K**: קומבו קבוע / בחירה; "מחיר בסיס" + תוספות; דוח Product Mix מראה פריטים בתוך קומבו.
- **Simphony** (העשיר ביותר): Primary + Side groups עם "Side Count", ברירות מחדל, **Upsizing** (גדלים 1–4, הגדלת תוספת בודדת), "Add Side Prices To Meal Price", "Only Print Priced Sides On Guest Check"; **חלוקת מס/מחיר יחסית** לפי מחיר à-la-carte של כל רכיב.
- **טאביט**: "Offer" כפריט מוביל + קבוצות קומבו (min/max, מעבר למקסימום — מחיר מלא). **שיטת חלוקה ברמת חנות: "חלוקה יחסית"** — כל רכיב מקבל מחיר מכירה × (מחיר ברירת המחדל שלו ÷ סכום מחירי ברירת המחדל), **upcharges לא נכנסים לחלוקה ונרשמים בערכם**; או "פריט ראשי" (הכול על המוביל). מאי 2025: הנחות יכולות לחול גם על תוספות בתשלום.

**אצלנו**: מוצר ארוחה עם משבצות (עיקרית/תוספת/שתייה), upcharge, ברירת מחדל, חובה/רשות; **שורה אחת בקבלה** עם רכיבים ו־upcharges כשורות משנה; **חלוקה יחסית בשיטת טאביט** (upcharges ותוספות בתשלום — לרכיב שלהם בערכם, הבסיס — יחסי למחירון), מוקפאת בזמן המכירה (בקליטה בענן); ניתוב ומלאי לכל רכיב; size-up דרך הגדלת מכירה.

### 2.4 הגדלות מכירה (Upsell)
- **Toast Menu Upsells** (נובמבר 2025): צמד תפריט, עצמאי, המלצת מודיפייר ("להוסיף אבוקדו?"), **שדרוג פריט**; מופעל ע״י "פריט מניע"; בקופה — **באנר כחול לא חוסם**, (+) להוספה, (X) לדחייה; בדשבורד — **שיעור קבלה**, מכירות מהגדלות, הגדלת חשבון ממוצע, מובילים לפי עובד.
- **Square Kiosk**: עד 3 הצעות במסך הסל; לא מציע פריט עם בחירות חובה שלא מולאו.
- **Simphony**: דף הצעות בקיוסק, פעם אחת לסשן; בקופה — סקריפטים.
- **טאביט** (אונליין): "קבוצות הצעה" לפי קטגוריה + כמות מינימלית; **כשכמה מתאימות — רק בעדיפות הגבוהה**.

**אצלנו**: כרטיס לא חוסם (כמו Toast), **פעם אחת לטריגר בהזמנה**, העדיפות הגבוהה מנצחת, ✕ לדחייה; סוגים: הוספה / שדרוג (כולל "הפוך לארוחה" ו־size-up); מדידה: הוצג / התקבל / נדחה / הכנסה.

### 2.5 הערות הכנה
- **Toast**: "Special Request" — מודיפייר טקסט חופשי שמודפס בבון; מסעדות בונות קבוצת "Allergies" (\*\*\*NUT ALLERGY\*\*\*) עם צבע KDS.
- **Square**: מודיפייר טקסט עד 150 תווים.
- **Lightspeed**: הערות ברמת כותרת / מנה / מושב — **בכחול**; אלרגנים — **באדום**.
- **ביקום**: הערות שולחן על מפת השולחנות.

**אצלנו**: צ׳יפים מוכנים לפי מוצר/קטגוריה + כלליים, טקסט חופשי, דגל "חשוב" (הפוך בבון), אלרגיה כסוג נפרד (§3.4). הערה ברמת מושב/מנה — שלב 2.

### 2.6 אלרגנים
- **Toast**: רשימה קבועה של 20, מוצגת ללקוח רק באונליין.
- **Square**: אלרגנים **ברמת מושב** מרשימה קבועה + טקסט חופשי; מודפסים **בכל FIRE** של המושב.
- **Lightspeed**: רשימה בבק־אופיס, ברמת הזמנה/מושב, באדום, עוברת למנות הבאות.
- **Simphony**: רשימה ארגונית, מחלקות אלרגנים לפי מחלקת פריט, עקיפה לפריט.
- **EU-14** (תקנה 1169/2011): גלוטן, סרטנים, ביצים, דגים, בוטנים, סויה, חלב, אגוזים, סלרי, חרדל, שומשום, סולפיטים, תורמוס, רכיכות. **ישראל** אימצה רשימה סגורה של 14 (בתוקף 2025, חובה 2028, מזון ארוז) ומדגישה גם **פול** (G6PD).
- **אף ספק לא בודק אוטומטית אלרגיה מוצהרת מול תגיות המנה** — הזדמנות.

**אצלנו**: 8 + 6 (EU-14), על מוצר ועל אפשרות; **בדיקה אוטומטית**: אלרגיה מוצהרת מול אלרגני המנה + האפשרויות שנבחרו → אזהרה; קופסה הפוכה בבון. פול ואזהרת כשרות (חלבי על בשרי) — הצעה לשלב 2.

### 2.7 מנות (Courses), Hold/Fire
- **Toast**: מנות ברמת קבוצת תפריט (פריטים יורשים, מלצר עוקף); Coursing חובה/רשות/כבוי בנפרד לדלפק ולשולחן; "שלח כל מנה בנפרד" (Send / Hold / Stay) או "שלח הכול ו־FIRE אוטומטי" (כשהמנה הקודמת הוכנה / לפי זמן).
- **Square**: מנות בשם, Hold / Fire; KDS "הצג מוצאות ומוחזקות" או "רק מוצאות".
- **Lightspeed**: ברירת מחדל מנה 1; "Send" מדפיס הכול, "Fire course" מאותת על הבאה; אייקון לא־הוצא / מוצא (להבה כתומה) / מוכן.
- **Simphony**: Hold and Fire לפי מושב/מנה; Dynamic Order Mode לשירות מהיר — לא משתלב עם hold & fire.
- **טאביט**: "שלב ארוחה" לפריט (ראשונות/עיקריות/קינוחים); **להבה ירוקה** — שולח ומדפיס; **להבה אדומה** — מסמן נשלח בלי להדפיס (לחם); "בחירת פריטים"; פריטים שלא נשלחו — **"ממתינים ל־Fire"** ואייקון להבה במפה.

**אצלנו**: מנה לכל שורה (ברירת מחדל מקטגוריה/מוצר), המנה הראשונה מוצאת והשאר "בהמתנה", "הוצא <מנה>", כותרת FIRE בבון; בדלפק — כבוי. FIRE אוטומטי ו"סמן כנשלח בלי הדפסה" — שלב 2.

### 2.8 עמדות מול מדפסות; מושבים
- **Toast**: Prep stations משויכות לתפריט/קבוצת תפריט ו**נורשות לפריטים ולמודיפיירים**; עקיפה; תחנה → מדפסות ו/או KDS, "שלח לאקספו".
- **Lightspeed**: מרכז ייצור (מדפסת/KDS), ניתוב דרך קבוצת הנהלת חשבונות.
- **Simphony**: פריט → **Print Class** → התקני הזמנה, עם התקן גיבוי והפניה.
- **טאביט**: **עמדות הכנה ממופות רבים־לאחד למדפסות**, ניתנות למיפוי מחדש באמצע משמרת; תוספות יכולות להיות מנותבות בנפרד.
- **ביקום**: KDS ("צ׳קר") מפצל לפי עמדת הכנה ומתריע על חריגת זמן.
- **מושבים**: Toast — חובה/רשות/כבוי, **"Share"** תמיד, פיצול לפי מושב בנגיעה; Lightspeed — ברירת מחדל "Shared"; Simphony — מספר מושב על כל פריט ומיון לפי מושב; טאביט — **"סועדים"**, העברת פריטים בין סועדים, פיצול תשלום.

**אצלנו**: שכבת **עמדה** בין התפריט למדפסות (כמו טאביט/Toast), בתוך מערכת המדפסות הקיימת (§9); סועדים עם "כללי" (=Share) (§7).

## 3. מודל נתונים (ענן)

כל הטבלאות ברמת **ארגון** (`tenant_id`), עם `company_id` אופציונלי — ריק = כל הארגון; מלא = החברה וכל החברות שמתחתיה. כך קבוצה "מידת עשייה" מוגדרת פעם אחת ומשמשת את כל הסניפים.

### 3.1 קבוצות ואפשרויות

**`modifier_groups`**

| עמודה | סוג | הערות |
|------|-----|-------|
| `id`, `tenant_id`, `company_id` | uuid | `company_id` null = כל הארגון |
| `name` | text(100) | "מידת עשייה", "תוספות להמבורגר" |
| `kind` | `choice` \| `addon` \| `removal` | איך מודפס: choice — כמות שהוא ("מדיום"); addon — "+ גבינה"; removal — **"בלי עגבנייה"** מודגש |
| `min_select` | int ≥0 | 1 = חובה |
| `max_select` | int ≥1 או null | null = ללא הגבלה |
| `free_count` | int ≥0 | N יחידות בחירה ראשונות חינם — **הזולות ביותר** (לא תלוי בסדר הבחירה, כך שעריכה לא משנה מחיר) |
| `allow_quantity` | bool | אפשר לבחור אפשרות יותר מפעם אחת (×2 שוט), נספר ב־max |
| `allow_pre` | bool | מקדימים מעט / הרבה / בצד |
| `sort_order`, `is_active`, `created_at`, `updated_at` | | |

**`modifier_options`**

| עמודה | סוג | הערות |
|------|-----|-------|
| `id`, `group_id` | uuid | |
| `name` | text(100) | "גבינה צהובה" |
| `kitchen_name` | text(60) | אופציונלי, קצר למטבח ("צהובה") |
| `price` | numeric(10,2) | תוספת המחיר, 0 = חינם |
| `is_default` | bool | מסומנת מראש |
| `allergens` | json[] | קודים מ־§3.4 |
| `linked_product_id` | uuid null | מוצר במלאי ("גבינה צהובה 1 פרוסה") — מלאי ודוח |
| `sort_order`, `is_active` | | |

**אימות הגדרה** (שרת): `0 ≤ min ≤ max`; `max ≥ 1`; `free_count ≤ max` (כשמוגדר); מספר ברירות המחדל ≤ max; קבוצת חובה חייבת אפשרות פעילה אחת לפחות; removal — בלי מקדימים ובלי כמות.

### 3.2 שיוך לקטגוריה ולמוצר — מוצר גובר

**`modifier_links`**: `(tenant_id, target_type ∈ {category, product}, target_id, group_id NULLABLE, sort_order)`.

- הקבוצות של מוצר = **הרשימה שלו** אם יש לו שורות; אחרת של הקטגוריה שלו; אחרת של ההורה שלה… (ירושה בעץ).
- שורה עם `group_id = NULL` = **"ללא תוספות" מפורש** — עוצרת ירושה (מוצר בקטגוריה עם תוספות שלא צריך אותן).
- רשימה של מוצר **מחליפה** את רשימת הקטגוריה, לא מתווספת — בדיוק כמו `kitchen_printer_routes` ו־`ticket_mode`. בדשבורד מוצג "לפי הקטגוריה: מידת עשייה, תוספות" כדי שיהיה ברור מה ירש.
- סדר הקבוצות בגיליון = `sort_order` של השיוך.

### 3.3 הערות הכנה מוכנות

**`prep_note_presets`**: `(tenant_id, company_id, target_type ∈ {all, category, product}, target_id, text(60), is_important, sort_order)`.

- הצ׳יפים של מנה = הצ׳יפים של המוצר אם יש; אחרת של הקטגוריה (בירושה בעץ); **ובנוסף תמיד** הצ׳יפים הכלליים (`all`): "בלי מלח", "לילד", "להוציא ראשון", "לחתוך לחצי".
- דוגמאות: קפה — חלב סויה / חלב שקדים / רותח / חזק / חצי־חצי / בכוס זכוכית; המבורגר — חתוך לחצי / רוטב בצד / לחמנייה ללא גלוטן.
- `is_important`: צ׳יפ שמסמן את ההערה כ"חשובה" אוטומטית ("להוציא ראשון", "לילד").
- בשורת המכירה: `notes` (רשימת צ׳יפים + טקסט חופשי) ו־`important` (bool). **חשוב** מודפס בבון בפס הפוך (לבן על שחור) ובראש השורה.

### 3.4 אלרגנים

רשימה **קבועה** (קודים באנגלית, תצוגה בעברית):

| peanuts | בוטנים | עיקרי |

- **בקופה**: בגיליון — צ׳יפים של אלרגני המנה; בעגלה — סימן ⚠ ליד שורה עם אלרגיה מוצהרת.

- **בבון**: "⚠ אלרגיה: בוטנים, שומשום" — קופסה הפוכה, מודגשת, מעל הפריטים של השורה.

### 3.5 ארוחות

**`meal_slots`**: `(id, tenant_id, product_id = מוצר הארוחה, name ("עיקרית"/"תוספת"/"שתייה"), min_select (0/1), max_select (≥1, ברירת מחדל 1), sort_order)`.
**`meal_slot_options`**: `(id, slot_id, product_id = רכיב, upcharge numeric(10,2), is_default, sort_order)`.

- מוצר עם משבצת אחת לפחות **הוא ארוחה** (`isMeal` בקופה).
- מחיר הארוחה = מחיר מוצר הארוחה (מחירון/מחיר סניף רגיל) + upcharges שנבחרו + שינויים בתשלום של הרכיבים.
- **רכיב שומר על התוספות וההערות שלו**: בבחירת "המבורגר" במשבצת העיקרית נפתחות קבוצות ההמבורגר (מידת עשייה, תוספות…), כמו כשמוכרים אותו לבד.
- **Size-up**: "הגדל ארוחה" = הגדלת מכירה מסוג `upgrade` ממוצר ארוחה רגילה לארוחה גדולה (§6) — הבחירות עוברות.
- ארוחה מקוננת (ארוחה בתוך ארוחה) — אסורה. רכיב לא יכול להיות מוצר ארוחה.

### 3.6 הגדלות מכירה

**`upsell_rules`**:

| עמודה | הערות |
|------|-------|
| `id`, `tenant_id`, `company_id`, `name` | |

| `trigger_ids` | json[] |
| `action` | `add` — הוסף מוצר (צ׳יפס ליד המבורגר); `upgrade` — החלף את השורה במוצר אחר (המבורגר → ארוחת המבורגר; ארוחה → ארוחה גדולה) |
| `product_id` | המוצר המוצע |
| `message` | "רוצה להפוך לארוחה?" — ריק = טקסט ברירת מחדל |
| `show_price` | מציג מחיר (add: מחיר המוצר; upgrade: ההפרש "+₪12") |

שורה שנוספה מהגדלה נושאת `upsellRuleId` (בפרטי השורה ובעמודה `transaction_items.upsell_rule_id`) — כך הכנסה מהגדלות נמדדת מהמסמכים עצמם.

### 3.7 מנות (Courses)

**`menu_courses`**: `(id, tenant_id, company_id, name, sort_order, is_active)` — "מנות ראשונות", "עיקריות", "קינוחים", "שתייה".
`products.course_id`, `categories.course_id` — ברירת מחדל; מוצר גובר על קטגוריה, קטגוריה יורשת מההורה. שורה בלי מנה = "ללא מנה" (יוצאת מיד).

### 3.8 שורת מכירה — פרטים (`details`)

נשמר בקופה (`transaction_items.detailsJson`), נשלח לענן (`items[].details`), נשמר בענן (`transaction_items.details` JSON) ומפורק לשורות דוח (`transaction_item_parts`):

```json
{
  "v": 1,
  "basePrice": 52.00,
  "modifiers": [
    {"groupId": "…", "groupName": "מידת עשייה", "kind": "choice",
     "optionId": "…", "name": "מדיום", "kitchenName": null,
     "price": 0, "qty": 1, "pre": null, "linkedProductId": null, "charged": 0}
  ],
  "notes": ["חתוך לחצי"], "noteText": "בלי מלח", "important": false,
  "allergies": ["peanuts"], "allergens": ["gluten", "milk"],
  "seat": 2, "course": {"id": "…", "name": "עיקריות"},
  "upsellRuleId": null,
  "meal": {
    "productId": "…", "name": "ארוחת המבורגר",
    "components": [
      {"slotId": "…", "slotName": "עיקרית", "productId": "…", "name": "המבורגר",
       "categoryId": "…", "listPrice": 52.00, "qty": 1, "upcharge": 0,
       "modifiers": [ … ], "notes": [], "noteText": null}
    ]
  }
}
```

- `price` = מחיר ליחידת אפשרות; `charged` = מה שחויב בפועל ליחידת שורה (אחרי "N חינם" ו"הרבה ×2"). `basePrice` = מחיר הבסיס בזמן המכירה.
- `unitPrice` של השורה = `basePrice + Σ charged` (+ upcharges ושינויים של רכיבים). **הקופה היא מקור האמת למחיר** — השרת לא מחשב מחדש ולא דוחה מסמך בגלל תפריט (מסמך פיסקלי לא נדחה; קופה אופליין עם הגדרה ישנה).
- `listPrice` של רכיב = מחיר הקטלוג של הרכיב בזמן המכירה (בסיס ההקצאה).

### 3.9 מגבלות, מכסות בארוחה, מימוש מאוחר וריפילים

שאלת הלקוח: "ארוחת בוקר — כמה ביצים מותר? יש הגבלה או אין? כמה פעמים אפשר להזמין קולה? הזמינו קולה ומגיעה להם עוד שתייה — האם רואים מה **נשאר** בארוחה?"

**1. מגבלה לאפשרות** — `modifier_options.max_qty` (null = ללא הגבלה), בנוסף ל־`max_select` של הקבוצה ול־`free_count`.
- דוגמה: קבוצת "תוספות לביצים" עד 5; "ביצים" עד 3; "גבינה" ללא הגבלה משלה.
- בגיליון: מונה "ביצים 2/3", ה־+ כבוי במקסימום (של האפשרות או של הקבוצה).
- מעל 1 דורש `allow_quantity`; לא יותר מ־`max_select`. נאכף בשרת (`validate_picks` → `option_above_max`) ובקופה.

**2. כמויות במשבצת ארוחה** — `meal_slots.quantity` = כמה פריטים מהמשבצת כלולים בארוחה אחת ("ארוחת בוקר זוגית": 2 שתייה חמה, 2 מנות ביצים, סלט אחד).
- `min_select` — כמה חובה לבחור בהזמנה; `max_select` — כמה מותר לבחור בהזמנה (≤ `quantity`).
- `allow_repeat` — אותו מוצר יכול למלא כמה פריטים (שתי קולות).
- `deferred` ("להזמין אחר כך") — מה שלא נבחר בהזמנה אפשר לקחת מאוחר יותר, בלי תשלום.

**3. יתרות בארוחה (מה נשאר)**
- לכל שורת ארוחה, לכל משבצת: **כלול** = `quantity × כמות השורה` (שורה בכמות 2 = זכאות כפולה); **מומש** = רכיבים שנבחרו בהזמנה (× כמות השורה) + פריטים שנלקחו אחר כך; **נשאר** = כלול − מומש.
- בעגלה ובהזמנת שולחן, מתחת לארוחה: **"נשאר בארוחה: שתייה ×1"** — נגיעה פותחת את הפריטים המותרים; בחירה מוסיפה **שורה משלה** במחיר 0 (או ה־upcharge אם בחרו שדרוג), מקושרת לארוחה (`details.mealRef` = הפניה לשורת הארוחה, המשבצת וסוג `deferred`).
- שורה כזו נשלחת למטבח/לבר **כשהיא נוספת** (בשליחה הבאה), ובבון: **"מתוך ארוחה: ארוחת בוקר · שולחן 4"**.
- למה שורה נפרדת ולא רכיב בתוך שורת הארוחה: הבון של שולחן נשלח לפי הפרש שורות; שורה חדשה נשלחת בדיוק פעם אחת, והקבלה מראה מה נלקח ומתי. **הקצאת ההכנסה של הארוחה לא משתנה** — היא מתחלקת בין הרכיבים שנבחרו בהזמנה; השורה המאוחרת נושאת 0 ₪ או את ה־upcharge בלבד, וכמותה נספרת ביחידות שנמכרו של המוצר.
- **בתשלום**: מה שלא מומש לא מזוכה (ברירת מחדל). שורת הארוחה נכתבת עם `details.entitlements` (כלול / מומש / נשאר לכל משבצת); פרמטר הקופה `receiptShowUnredeemed` מדפיס בקבלה "לא מומש: שתייה ×1"; דוח הארוחות סופר מה לא מומש, מה נלקח אחר כך ומה היו הריפילים.

**4. ריפילים וחזרות ("כמה פעמים אפשר להזמין קולה")**
- משבצת (`meal_slots.refillable`, `max_refills`) או מוצר (`products.refillable`, `max_refills`; null = ללא הגבלה).
- כל ריפיל הוא שורה של 0 ₪ מקושרת (`mealRef.kind = refill`, או לשורת המוצר), מסומנת **"ריפיל 2/3"**, ונשלחת לבר. מעל המכסה — הכפתור כבוי ("נוצלו כל הריפילים").
- מכסה לשורת ארוחה בכמות Q: `max_refills × Q`.
- **`products.max_per_order`** (רשות, למשל מוצר מבצע — 1 להזמנה): הוספה מעל המכסה נחסמת בהודעה ברורה ("ניתן להזמין עד 1 ממוצר זה").

**5. הקצאת הכנסה — ללא שינוי**: שורות מאוחרות וריפילים נושאות 0 ₪ או את ה־upcharge בלבד, ולכן ההקצאה של מחיר הארוחה נשארת מדויקת; הכמות שלהן נספרת בכמות שנמכרה.

## 4. תמחור ואימות בקופה

1. **חובה**: קבוצה עם `min ≥ 1` — כפתור "הוסף" כבוי עד שנבחרו לפחות `min`; תגית "חובה" ליד הקבוצה, ואדומה אם המלצר ניסה להוסיף.
2. **מקסימום**: `max = 1` → בחירה אחת (radio); `max > 1` → סימון (checkbox) עד max; בחירה מעבר ל־max — חסומה עם רטט קל.
3. **כמות לאפשרות** (`allow_quantity`): + / − על האפשרות; כל יחידה נספרת ב־max.
4. **N חינם**: מכל יחידות הבחירה בקבוצה, `free_count` היחידות **הזולות** חינם.
   דוגמה: max 5, free 2, נבחרו בצל (2), פטריות (4), ביצה (5) → בצל ופטריות חינם, ביצה 5 ₪.
5. **מקדימים**: הרבה = מחיר × 2; מעט / בצד = מחיר רגיל. מקדים על אפשרות חינם — חינם.
6. **ברירות מחדל** מסומנות מראש, ונספרות כבחירה רגילה (במחיר שלהן).
7. מחיר שורה = `(בסיס + Σ חיובי אפשרויות) × כמות`. ארוחה: `(מחיר ארוחה + Σ upcharge + Σ חיובי אפשרויות של רכיבים) × כמות`.
8. **מיזוג שורות**: שורה עם פרטים (תוספות, הערות, ארוחה, סועד, מנה) לא מתמזגת עם אחרת; הקשה חוזרת על מוצר פשוט ממשיכה להגדיל כמות כמו היום.
9. מוצר עם מחיר פתוח / שקיל — תוספות לא נתמכות בשלב זה (התנהגות כמו היום).

## 5. ארוחות — "לעשות נכון"

### 5.1 קבלה / מסמך מס
- **שורה אחת**: "ארוחת המבורגר  1 × 62.00"; מתחתיה מוזח: "המבורגר · מדיום · + גבינה (5.00)", "צ׳יפס גדול (+3.00)", "קולה זירו".
- תוספות **בתשלום** ורכיבים — מודפסים בקבלה; בחירות חינם והסרות — רק בבון (הקבלה ללקוח נשארת נקייה; מה שמסביר מחיר מופיע).
- למסמך המס זו שורה אחת (`unitPrice`, `totalPrice`) — שורות המשנה הן הסבר בלבד, לא שורות מסמך. כך אין שינוי במבנה החשבונית, ב־OpenFormat או ב־Z.

### 5.2 הקצאת הכנסה לרכיבים (Revenue allocation)
מטרה: "כמה המבורגרים מכרנו" — כולל בתוך ארוחות, וסכום הכסף **זהה בדיוק** לשורת הקבלה.

אלגוריתם (באגורות, לשורה):
1. `G` = ברוטו השורה (`totalPrice`), `D` = הנחות השורה (`discount + promotionDiscount`), `Q` = כמות.
2. לכל רכיב i: `E_i = round((upcharge_i + Σ charged של שינוייו) × qty_i × Q)` — **ישירות** לרכיב.
3. `B = G − Σ E_i` — מחיר הבסיס של הארוחות בשורה. מחולק לפי משקלות `L_i = listPrice_i × qty_i` בשיטת **השארית הגדולה** (floor, ואז האגורות שנשארו למי שהשבר שלו הגדול ביותר; שוויון — לפי סדר הרכיבים). כל `L_i = 0` → חלוקה שווה.
4. `gross_i = base_i + E_i` → `Σ gross_i = G` בדיוק.
5. `discount_i` = חלוקת `D` לפי משקלות `gross_i` (שארית גדולה) → `Σ = D` בדיוק.
6. `units_i = qty_i × Q`.

דוגמה: ארוחת המבורגר 62 ₪ (המבורגר 52, צ׳יפס 18, קולה 12 → סה״כ 82), "צ׳יפס גדול +3", "+ גבינה 5", כמות 1 → G = 70.00, E = {המבורגר 5.00, צ׳יפס 3.00, קולה 0}, B = 62.00 = 6200 אגורות → 6200×52/82 = 3931.71, 6200×18/82 = 1360.98, 6200×12/82 = 907.32 → floor: 3931 + 1360 + 907 = 6198; שתי האגורות שנשארו הולכות לשברים הגדולים (צ׳יפס .98, המבורגר .71) → 39.32 / 13.61 / 9.07 → ברוטו: 44.32 / 16.61 / 9.07 = **70.00**.

- ההקצאה מחושבת **בענן** בקליטת המסמך (מקור אחד לדוחות) ונשמרת ב־`transaction_item_parts`. זהה בקופה (`MealMath`) לבדיקות ולתצוגה.
- תעודת זיכוי: אותו חישוב על שורת הזיכוי (`totalPrice` שלה כבר נטו) — הזיכוי מתחלק לרכיבים באותו יחס.

### 5.3 מטבח
- הארוחה **מתפרקת לרכיבים בבון**: כל רכיב שורה משלו עם השינויים וההערות שלו, ומנותב לפי **המוצר והקטגוריה של הרכיב** (המבורגר → גריל, צ׳יפס → טיגון, קולה → בר). מתחת לכל רכיב: "(ארוחת המבורגר)" קטן.
- הערות/אלרגיות ברמת הארוחה מודפסות על **כל** רכיב.

### 5.4 מלאי
- תנועת מלאי לכל רכיב שמנוהל במלאי (`qty_i × Q`), ולכל אפשרות עם `linkedProductId` שמנוהל במלאי (`qty × Q`; הסרה לא מורידה). מוצר הארוחה עצמו — רק אם הוא מנוהל במלאי (בדרך כלל לא).
- זיכוי מחזיר את אותן כמויות.

### 5.5 מבצעים, הנחות, שוברים, זיכוי, פיצול
| נושא | כלל |
|------|-----|
| מבצעים | חלים על השורה כמוצר הארוחה (או המוצר עם תוספותיו) — `unitPrice` כולל תוספות. מבצע על "המבורגר" לא חל על המבורגר שבתוך ארוחה (הארוחה כבר מחיר חבילה). מבצע "קומבו" (סוג 7) ממשיך לחול על פריטים נפרדים בלבד. |
| לא מקבל הנחות | של מוצר הארוחה/המנה — חל על כל השורה כולל תוספות. דגל של רכיב — לא רלוונטי בתוך ארוחה. |
| הנחת שורה / סל | על השורה כולה (כולל תוספות); בדוחות — מתחלקת לרכיבים לפי §5.2. |
| שובר פריט (`ticket_mode`) | לפי מוצר השורה (הארוחה) — שובר לארוחה, לא לכל רכיב. |
| שובר הפקה | מכסה מוצר לפי **מחיר הבסיס**: ערך מכוסה ליחידה = נטו ליחידה × (בסיס ÷ מחיר יחידה). תוספות בתשלום נשארות לתשלום. שובר לארוחה מכסה את מחיר הארוחה; upcharges לתשלום. |
| זיכוי | שורה שלמה (או חלק מהכמות) — לפי מה ששולם (`RefundMath`). פרטי השורה מועתקים לשורת הזיכוי. אין זיכוי לרכיב בודד מתוך ארוחה (צריך לזכות ארוחה ולמכור מחדש). |
| פיצול תשלום | ללא שינוי — מתבצע על המסמך. פיצול לפי סועד — שלב 2 (§7). |

## 6. הגדלות מכירה (Upsell)

- **מתי**: אחרי שנוספה שורה (או נסגר גיליון התוספות) של מוצר שעונה לטריגר, בשעות הפעילות, כשהפרמטר "הגדלות מכירה" פעיל.
- **לא**: במצב זיכוי; אם ההצעה (add) כבר בסל; אם השורה כבר ארוחה (upgrade לארוחה); יותר מפעם אחת לאותה שורה; כשיש כרטיס פתוח (הכרטיס החדש מחליף).
- **תצוגה**: כרטיס צף לא חוסם מעל העגלה/הסכום: אייקון ✨, הטקסט, המחיר ("+₪12"), כפתור "הוסף"/"שדרג", ✕. נעלם לבד אחרי ~8 שניות או בפעולה הבאה. הכרטיס **לא** עוצר הוספות.
- **קבלה**:
  - `add` — מוסיף שורה של המוצר (אם יש לו קבוצות חובה — נפתח הגיליון שלו).
  - `upgrade` — מחליף את השורה: אם היעד ארוחה, המוצר המקורי נכנס למשבצת שבה הוא מותר **עם השינויים וההערות שלו**, שאר המשבצות בברירת מחדל; אם חסרה בחירת חובה בלי ברירת מחדל — נפתח בונה הארוחה בשלב החסר.
- **סטטיסטיקה**: הקופה סופרת לכל כלל ויום shown/accepted/dismissed ושולחת לענן (`POST /sync/{m}/upsell-stats`, ערכים מוחלטים). השורה שהתקבלה נושאת `upsellRuleId`. דוח: הוצג, התקבל, נדחה, שיעור קבלה, הכנסה.
- פרמטר קופה: `upsellEnabled` (ברירת מחדל: מופעל).

## 7. סועדים בשולחן (Seat assignment) — רשות

- בראש הזמנת שולחן: פס "סועד פעיל": **כללי** · 1 · 2 · … · N (N = מספר הסועדים בשולחן, + להוספה). לחיצה ארוכה = שינוי שם ("דנה").
- שורה חדשה נכנסת לסועד הפעיל (`seat`), "כללי" = `null` (משותף).
- העברה: בעריכת שורה — בחירת סועד.
- העגלה מקובצת לפי סועד (כותרת "סועד 2 · דנה").
- בבון: "סועד 2 · דנה" מתחת לשם המנה.
- השמות נשמרים בשולחן (`TableExtras.seatNames`).
- מכין פיצול חשבון לפי סועד (שלב 2): כל שורה יודעת למי היא שייכת.
- בדלפק (לא שולחן) — אין סועדים.
- פרמטר קופה `tableSeats` (ברירת מחדל: מופעל; כבוי = הפס לא מוצג).

## 8. מנות (Courses) — Hold / Fire

- כל שורה בשולחן מקבלת מנה (ברירת מחדל מהמוצר/קטגוריה; ניתן לשנות בעריכת שורה).
- מצב מנה בהזמנה: **מוצאת** (fired) או **בהמתנה** (held). ברירת מחדל: המנה הראשונה בסדר שיש לה שורות מוצאת; השאר בהמתנה — **[לאישור]** (חלופה: הכול מוצא אלא אם המלצר סימן "החזק").
- "שלח למטבח": נשלחות רק שורות של מנות מוצאות (ושורות בלי מנה). שורות בהמתנה מסומנות "בהמתנה" בעגלה.
- "הוצא <מנה>" (FIRE): מסמן את המנה כמוצאת ושולח את שורותיה; בבון כותרת "🔥 הוצא: עיקריות".
- בבון: השורות מקובצות לפי מנה עם כותרת המנה.
- דלפק: מנות מתעלמות — הכול יוצא מיד.
- פרמטר קופה `coursesEnabled` (ברירת מחדל: כבוי — התנהגות של היום).

## 9. עמדות הכנה (Stations)

מה שקיים (סוכן המדפסות): `kitchen_printer_routes` — מוצר/קטגוריה → מדפסת, לכל **סניף**; מוצר גובר על קטגוריה; ירושה בעץ; "ללא בון" מפורש; הקופה מקבלת `categoryRoutes`/`productRoutes` כבר מחושבים.

ההרחבה (לא מערכת שנייה):
- **`kitchen_stations`** `(id, tenant_id, company_id, name, sort_order)` — "גריל", "טיגון", "סלטים", "פיצה", "קינוחים", "קפה", "בר".
- מוצר/קטגוריה משויכים לעמדה: `products.station_id`, `categories.station_id` (מוצר גובר, ירושה בעץ).
- עמדה → מדפסות לכל סניף: שורות ב־`kitchen_printer_routes` עם `target_type = 'station'`.
- **חישוב הניתוב** (בענן, בתוך שירות המדפסות הקיים, בזמן בניית `categoryRoutes`/`productRoutes` לקופה): ניתוב ישיר של מוצר > עמדה של מוצר > ניתוב ישיר של קטגוריה (בירושה) > עמדה של קטגוריה (בירושה). כך הקופה ממשיכה להשתמש ב־`KitchenRouting` בלי שינוי.
- שם העמדה מודפס בראש הבון ("גריל"), והבון מפוצל לפי עמדה (כשמדפסת אחת משרתת כמה עמדות — כותרת לכל עמדה).

## 10. זרימת נתונים

### 10.1 סנכרון קטלוג (ענן → קופה)
`GET /sync/{m}/catalog` מחזיר בנוסף:
- בשורת מוצר: `allergens`, `courseId`, `stationId`, `isMeal`; בשורת קטגוריה: `courseId`, `stationId`.
- בלוק **`menu`** שלם: `updatedAt`, `groups` (עם `options`), `links` (`categories`/`products` → רשימת מזהי קבוצות, `[]` = ללא), `notes` (`all`/`categories`/`products`), `meals` (מוצר → משבצות), `upsells`, `courses`, `stations`.
- **מלא**: תמיד. **דלתא**: רק אם משהו בתפריט השתנה אחרי `since` (חותמת `menu_sync_state.changed_at` לארגון, מתעדכנת בכל כתיבה כולל מחיקה); אחרת `menu` חסר → הקופה שומרת את מה שיש.
- הבלוק נשלח שלם — מחיקה פשוט נעלמת ממנו (אין צורך ב־tombstones). מסונן לחברת הסניף (וחברות־אב) + ארגוני.
- `get_catalog_change_watermark_for_machine` כולל את חותמת התפריט, כדי שקופה לא תיראה "מעודכנת" כשהתפריט השתנה.

### 10.2 בקופה
- הבלוק נשמר כ־JSON בטבלת ההגדרות (Room, `menu.json`) — כמו המבצעים — ונקרא לזיכרון (`MenuRepository`). הכול עובד **אופליין**.
- Room: `products.allergensJson`, `products.courseId`, `categories.courseId`, `transaction_items.detailsJson` (מיגרציה חדשה).

### 10.3 מכירה (קופה → ענן)
- `items[].details` (§3.8) ו־`items[].upsellRuleId`.
- בענן: `transaction_items.details` (JSON), `transaction_items.upsell_rule_id`, ופירוק ל־`transaction_item_parts`:
  `(transaction_id, item_id, kind ∈ {component, modifier}, component_index, product_id, group_id, option_id, name, pre, quantity, unit_price, gross, discount)`.
  במסמך שנשלח שוב — מוחלף כמו השורות.
- המלאי — `stockMovements` מהקופה (כולל רכיבים ומוצרים מקושרים), כמו היום.

### 10.4 דוחות
| דוח | מה |
|-----|----|
| מכירות לפי מוצר | ברירת מחדל `meals=components`: שורת ארוחה מוחלפת ברכיבים (יחידות, ברוטו והנחה מוקצים); עמודה "בתוך ארוחות". `meals=meals` — כמו היום. |
| מכירות תוספות | לכל אפשרות: קבוצה, כמה פעמים, הכנסה, כמה הסרות; לפי מוצר בסיס. |
| ארוחות | לכל ארוחה: כמות, הכנסה, פירוק לרכיבים ו־upcharges. |
| הגדלות מכירה | לכל כלל: הוצג / התקבל / נדחה / שיעור קבלה / הכנסה מהשורות שהתקבלו. |

### 10.5 תאימות לאחור
- שורה בלי `details` = שורה רגילה בכל מקום.
- קופה ישנה: מתעלמת מ־`menu` ומשדות חדשים; ממשיכה למכור.
- שרת ישן: אין `menu` → אין גיליון תוספות, כל מוצר מתווסף בנגיעה כמו היום.
- `details` לא מאומת מול ההגדרות בשרת — מסמך לעולם לא נדחה בגלל תפריט.

## 11. UX בקופה (בסגנון iOS, פרימיום)

- **מוצר בלי תוספות** — נגיעה אחת מוסיפה, בדיוק כמו היום. אין שום האטה.
- **מוצר עם קבוצת חובה / ארוחה** — נגיעה פותחת **גיליון תחתון**:
  - כותרת: שם, מחיר חי, אלרגני המנה כצ׳יפים.
  - קבוצות לפי הסדר; תגית "חובה" / "עד 5" / "2 חינם"; radio/checkbox גדולים; +/− לכמות; מקדימים כגלולה מתחלפת (רגיל → מעט → הרבה → בצד).
  - ברירות מחדל מסומנות.
  - הערות: צ׳יפים מוכנים, שדה טקסט, מתג "חשוב".
  - אלרגיה: שורת צ׳יפים "אלרגיה ל…" עם אזהרה אדומה כשהמנה מכילה.
  - בתחתית: כמות − 1 +, וכפתור ראשי **"הוסף ₪xx"** (כבוי עד שהחובה מולאה; לחיצה עליו כשכבוי גוללת לקבוצה החסרה ומסמנת אותה באדום).
- **רק קבוצות רשות** — נגיעה מוסיפה מיד; תג "+" קטן בפינת האריח פותח את הגיליון.
- **עריכת שורה** בעגלה — פותחת את אותו גיליון עם הבחירות; "עדכן".
- **בונה ארוחה** — שלבים: פס התקדמות (עיקרית · תוספת · שתייה · סיכום), בכל שלב אריחי הרכיבים עם upcharge, ברירת מחדל מסומנת; רכיב עם תוספות — הקבוצות שלו נפתחות באותו שלב; "הבא" / "הקודם"; סיכום עם הערות וכמות; "הוסף ₪xx".
- **עגלה**: שם המנה, ומתחתיה שורות משנה קטנות (בחירות, "+ גבינה 5.00", **בלי בצל**, הערה, ⚠ אלרגיה, "סועד 2"); ארוחה — רכיבים עם הבחירות שלהם.
- **כרטיס הגדלת מכירה** — §6.

## 12. UX בענן (דשבורד)

- **"תוספות ושינויים"** (תחת קטלוג): רשימת קבוצות בכרטיסים מעוגלים; עורך קבוצה: שם, סוג (סגמנט: בחירה / תוספת / הסרה), מינ׳/מקס׳, חינם, כמות, מקדימים (מתגים), אפשרויות בגרירה (שם, שם למטבח, מחיר, ברירת מחדל, אלרגנים, מוצר מקושר); שיוך לקטגוריות.
  לשוניות: קבוצות · הערות מוכנות · מנות · (עמדות).
- **טופס מוצר** — סעיף "תוספות, הערות ואלרגנים": אלרגנים (צ׳יפים), קבוצות (ירושה מהקטגוריה / רשימה משלו / ללא), הערות מוכנות, מנת ברירת מחדל; סעיף **"ארוחה"**: משבצות, רכיבים, upcharge, ברירת מחדל.
- **טופס קטגוריה** — קבוצות והערות לקטגוריה.
- **"הגדלות מכירה"**: רשימת כללים + עורך (טריגר, פעולה, מוצר, טקסט, מחיר, שעות, ימים) + סטטיסטיקה.
- **דוחות**: מכירות תוספות, ארוחות, הגדלות מכירה; "מכירות לפי מוצר" עם מתג "פירוק ארוחות".

## 14. בדיקות קבלה

1. המבורגר עם "מידת עשייה" (חובה, 1) ו"תוספות" (0–5, 2 חינם): נגיעה פותחת גיליון; "הוסף" כבוי עד בחירת מידה; בצל+פטריות+ביצה → רק ביצה מחויבת; המחיר בכפתור מתעדכן חי.
2. קולה בלי תוספות — נגיעה אחת, שורה מתווספת, נגיעה נוספת מגדילה כמות.
3. מוצר בקטגוריית "המבורגרים" בלי רשימה משלו — מקבל את קבוצות הקטגוריה; מוצר עם "ללא תוספות" — מתווסף מיד.
4. אלרגיה לחלב על מנה עם "גבינה" — אזהרה אדומה בגיליון ובעגלה; בבון קופסה הפוכה.
5. ארוחת המבורגר: עיקרית (המבורגר → מידה), תוספת (צ׳יפס גדול +3), שתייה (ברירת מחדל קולה) → שורה אחת 65 ₪; בקבלה שורת משנה לכל רכיב; בבון: המבורגר לגריל, צ׳יפס לטיגון, קולה לבר.
6. דוח מכירות לפי מוצר: 3 המבורגרים לבד + 2 בארוחות = 5; סכום ההכנסה המוקצית = סכום השורות באגורה.
7. זיכוי ארוחה — שורה אחת מזוכה, מלאי הרכיבים חוזר, הדוח מוריד את הרכיבים.
8. "1+1 על המבורגרים" — לא חל על המבורגר שבתוך ארוחה; חל על המבורגר לבד כולל תוספותיו.
9. הגדלת מכירה "המבורגר → ארוחה": כרטיס מופיע, לא חוסם; "שדרג" → השורה הופכת לארוחה עם ההמבורגר ותוספותיו; הדוח סופר הצגה וקבלה.
10. אופליין: עריכת קבוצה בענן בזמן שהקופה מנותקת — הקופה ממשיכה עם ההגדרה הקודמת; אחרי חיבור — דלתא מביאה את התפריט החדש.
11. קופה ישנה מול שרת חדש ושרת ישן מול קופה חדשה — מכירה רגילה עובדת.
12. שולחן עם 4 סועדים: מנות לסועד 2 ו־3, בבון "סועד 2"; מנות: ראשונות נשלחות, עיקריות "בהמתנה", "הוצא עיקריות" שולח עם כותרת FIRE.
13. "ביצים" עד 3 בקבוצה של עד 5: אחרי 3 ה־+ של ביצים כבוי ("ביצים 3/3"), גבינה עדיין מתווספת; השרת דוחה הגדרה של 4 לאפשרות בקבוצה של 3.
14. ארוחת בוקר זוגית ×1 (שתייה: כמות 2, מאוחר מותר): הזמינו קולה → "נשאר בארוחה: שתייה ×1"; אחרי חצי שעה בשולחן: נגיעה → קפה → שורת 0 ₪ "מתוך ארוחה", נשלחת לבר בשליחה הבאה; היתרה מתאפסת. ארוחה ×2 = זכאות כפולה.
15. קולה עם ריפיל עד 2: שני ריפילים של 0 ₪ ("ריפיל 1/2", "ריפיל 2/2"), השלישי חסום. מוצר מבצע עם "עד 1 להזמנה": השני נחסם בהודעה.

## 15. החלטות פתוחות [לאישור]

1. **N חינם** — הזולות חינם (נבחר; צפוי ונוח למסעדן) או לפי סדר הבחירה?
2. **שובר הפקה** — מכסה רק מחיר בסיס (נבחר) או גם תוספות בתשלום?
3. **מנות** — ברירת מחדל: המנה הראשונה יוצאת והשאר בהמתנה (נבחר) או הכול יוצא עד שמסמנים "החזק"?
4. **קבלה** — להדפיס גם בחירות חינם והסרות (נבחר: לא — רק בבון)?
5. **מוצר עם קבוצת חובה שיש לה ברירת מחדל** — לפתוח גיליון (נבחר, לפי הבקשה) או להוסיף מיד עם ברירת המחדל?
