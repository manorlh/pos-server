# תפקידים והרשאות לעובדי קופה + מודול מגירת מזומן

> מסמך אפיון/מימוש — R2M POS (ענן `pos-server`: `server/` + דשבורד `client/`; קופה `pos-android`).
> מקור הדרישות: בקשת הבעלים (07.10.2026) — "הרשאות לקופאי: האם מותר לו למכור, האם מותר לו בכלל מודול
> שולחנות, למי מותר עבודה עם מחשבון — תאפשר דינמיות ליצור הרשאות נוספות ותפקידים", ומסמך האפיון
> "אפיון הרשאות ובקרת פתיחת מגירת מזומן לקופה" (להלן: **אפיון המגירה**, סעיפים §1–§20).

## 1. תמצית

* **קטלוג הרשאות אחד** (ענן: `server/app/services/till_permissions.py`, קופה: `domain/PermissionService.kt` —
  אחד-לאחד, נבדק מול fixture משותף `till_permissions_matrix.json` בשני המאגרים).
* **שלושה מצבים** לכל הרשאה: **מותר** (`allow`) / **דורש אישור מנהל** (`approval`) / **אסור** (`deny`),
  ולחלק מההרשאות **סף** (`maxPercent` להנחה, `maxAmount` לזיכוי, ל-Cash Out ולהפקדה).
* **תפקידים לכל חברה**: מובנים (מלצר, קופאי, אחמ״ש, מנהל + שני "תפקידי מעבר" שמשמרים את ההתנהגות של
  היום) ומותאמים אישית (שם, תיאור, מטריצה, ספים). כל עובד קופה משויך לתפקיד אחד, עם **חריגות אישיות**
  אופציונליות.
* **הקופה מחליטה לבד, גם בלי רשת**: הענן מחשב לכל עובד פרופיל **אפקטיבי** (כל קוד → מצב, וספים) ושולח
  אותו ברשימת העובדים; הקופה שומרת אותו ב-Room ומחליטה ממנו. אישור מנהל — PIN מול ה-hash שבקופה (כמו
  היום), לפעולה אחת בלבד, המבקש והמאשר נרשמים, המשתמש המחובר לא מתחלף.
* **מגירת מזומן**: כל פתיחה עוברת דרך `CashDrawerService.requestOpen()` בסדר הבדיקות של §19; כל ניסיון
  (מאושר / חסום / נכשל) נרשם ב-audit מקומי ומסונכרן לענן בלי כפילויות; Cash In / Out / הפקדה וספירות
  נרשמים כתנועות נפרדות; יתרה צפויה + snapshots; Blind Count; חריגות לפי §11; דוחות + KPI + ציר זמן.

התפקידים): מוסיפים — לא משנים ולא ממחזרים.

### 2.2 תפקידים וירושה

טבלה `till_roles` (לכל חברה): `builtin_key` (מובנה) או `base_key` (התבנית של תפקיד מותאם), שם, תיאור,
`permissions` ו-`limits` — **רק מה שהתפקיד קובע בעצמו**. השאר — מהתבנית.

**סדר ההחלטה, לכל קוד ולכל סף בנפרד:**

```
חריגה אישית של העובד  →  ערך התפקיד  →  התבנית של התפקיד  →  אסור
```

* התבנית של תפקיד מובנה היא עצמו; של תפקיד מותאם — המובנה שממנו נוצר (ריק = "קופאי"); שכפול כותב את
  המטריצה האפקטיבית של המקור במלואה (שינוי מאוחר במקור לא מזיז את העותק).
* קוד שנוסף לקטלוג בגרסה מאוחרת מקבל ערך בכל תפקיד דרך התבנית — בלי מיגרציה. קוד לא מוכר — לעולם לא
  ניתן.
* `pos_users.till_role_id` (NULL = עוד לא שויך) + `pos_users.permission_overrides`
  (`{"states": {...}, "limits": {...}}`).
* תפקידים הם של **חברה** (חברת הסניף של העובד); תת-חברה מגדירה תפקידים משלה (אין ירושה בין חברות).

נוכחות, אשראי לא ידוע), "אסור" רק לאישור פעולות מגירה של אחרים (שהיה של מנהל בלבד), והשאר מותר
("כרגע אין הרשאות, כולם יכולים לעשות הכל").

### 2.4 תאימות לקופות ישנות

`pos_users.role` (`cashier` / `shop_manager`) נשאר מה שקופה ישנה קוראת. בכל שיוך / עריכת תפקיד / חריגה
הוא נכתב מחדש: `shop_manager` רק כשהעובד רשאי **לבד** לכל מה שקופה ישנה מתירה למנהל לבד (אחרת `cashier` —
הכיוון הבטוח). כל שינוי כזה מעדכן את `updated_at` של העובד (משיכת העובדים בקופה) ומודיע לקופות הסניף.

### 2.5 הענן משתמש באותן הרשאות

אישור elevation בענן (`grantable_scopes_for_pos_user`, בדיקת session חי), כתיבת קטלוג על סמכות המפעיל,
מאשר מסמך (`approvals.verify_document_pos_approver`), מאשר נוכחות ומאשר שליטה בקיוסק — כולם קוראים
את הפרמטר האפקטיבי (`till_roles.pos_user_scopes` / `pos_user_allows`) במקום `pos_users.role`. עובד שלא
שויך — לפי תפקיד המעבר שלו, כמו קודם.

## 4. API

| | נתיב |
|---|---|
| קטלוג | `GET /till-permissions/catalogue` |
| תפקידים | `GET/POST /companies/{id}/till-roles`, `PUT /companies/{id}/till-roles/{roleId}`, `PUT …/till-roles/matrix`, `DELETE …/till-roles/{roleId}?reassignTo=` |
| ברירות מחדל | `POST /companies/{id}/till-roles/apply-spec-defaults` `{resetBuiltins, moveLegacyUsers}` |
| יומן | `GET /companies/{id}/till-roles/changes` |
| עובדים | `GET /companies/{id}/till-roles/users?shopId=`, `PUT /shops/{shopId}/pos-users/{id}/till-role` `{tillRoleId, overrides?, clearOverrides?}` |
| קופאים | `POST/PUT /shops/{shopId}/pos-users` מקבלים `tillRoleId`; מחזירים `tillRoleId`, `tillRoleName` |
| פרמטרי מגירה | `GET/PUT /companies/{id}/till-drawer-params` (רמה: company / shop / area / machine) |
| רשימת עובדים לקופה | `GET /sync/{machineId}/pos-users` — לכל שורה גם `tillRoleId`, `tillRoleKey`, `tillRoleName`, `permissions`, `limits` |
| מגירה (קופה) | `POST /sync/{machineId}/cash-drawer/events`, `POST /sync/{machineId}/cash-drawer/movements` — idempotent לפי id (201 / 200 / 409 ל-id של קופה אחרת) |
| דוחות מגירה | `GET /cash-drawer/events`, `GET /cash-drawer/movements`, `GET /cash-drawer/shifts/{id}/timeline` |

**מי:** קריאת תפקידים — סופר אדמין, מפיץ, מנהל חברה (על החברה ותת-החברות), מנהל סניף / אחמ״ש (חברת
הסניף שלו). הגדרת תפקידים — סופר אדמין, מפיץ, מנהל חברה. שיוך עובד — מי שמורשה לנהל את קופאי הסניף.
פרמטרי מגירה — מנהלי החברה בכל רמה, מנהל סניף ברמות של הסניף שלו. דוחות המגירה — כל תפקיד מלבד קופאי.

## 5. דשבורד

* **"תפקידים והרשאות"** (`/dashboard/till-roles`, הגדרות): מטריצה (הרשאות בקבוצות × תפקידים), לחיצה על תא
  מחליפה מותר → באישור → אסור, ספים מתחת לתא "מותר", שינויים מסומנים ונשמרים יחד (נשלח רק מה ששונה
  מהתבנית); תפקיד חדש (תבנית / שכפול), שינוי שם ותיאור, מחיקה (מותאם בלבד, עם תפקיד חלופי למשויכים);
  "החל ברירות מחדל לפי האפיון"; לשונית **עובדים** (שיוך + "הרשאות אישיות"); **פרמטרי מגירה** (לפי רמה,
  עם הערך שנורש); **יומן שינויים**.
* **"קופאים (POS)"**: בחירת "תפקיד והרשאות" במקום קופאי / מנהל סניף, שם התפקיד ברשימה, קישור לעמוד.
* **"מגירת מזומן"** (`/dashboard/cash-drawer`, דוחות): פתיחות + KPI, תנועות, ציר זמן משמרת (גם מעמוד
  המשמרת).
* **"חריגות" / "הגדרות חריגות"**: שמונה סוגי החריגות של המגירה (§6.6), עם הפעלה/כיבוי לפי רמה.
* **"יומן חריגות" / "התראות SMS על חריגות"**: חריגות המגירה נרשמות ביומן וניתן לבחור אותן בחוק התראה.
* **"הרשאות דשבורד"** (`app/services/dashboard_sections.py`, `client/src/lib/dashboardAccess.ts`): עמוד התפקידים
  ונתיבי `/companies/{id}/till-roles*` ו-`/till-permissions/catalogue` — לשונית "קופאים (POS)" (צפייה / עריכה;
  עריכת תפקידים ושיוך עובדים דורשים עריכה); פרמטרי המגירה (`/companies/{id}/till-drawer-params`) — "הגדרות
  קופות" (עריכה; קריאה גם למי שצופה בעמוד התפקידים); דוחות המגירה (`/cash-drawer/*`) — "דוחות" (צפייה), ציר
  הזמן של משמרת גם מ"זדים ומשמרות". שיוך תפקיד לעובד (`/shops/{id}/pos-users/{id}/till-role`) — "קופאים (POS)".

## 6. הקופה

### 6.1 `PermissionService` (domain, טהור)

`PermissionService.decide(profile, code, amount, percent, forceApproval, relaxApproval)` →
`Allowed` / `NeedsApproval(why: ROLE | OVER_LIMIT | SETTING)` / `Denied(why: ROLE | NOT_SIGNED_IN | SETTING)`;
`mayApprove(approver, code, amount, percent)` (מותר לבד בתוך הסף, ולפעולת מגירה גם `APPROVE_OPEN`).
`PermissionProfile.fromJson(permissionsJson, role)` — פרופיל הענן, או תפקיד המעבר כשאין (שרת ישן), וקוד שהשרת
לא שלח מקבל את ערך תפקיד המעבר. `TillAuthority` נשאר כחזית דקה מעל תפקיד המעבר בלבד.

`OperatorSession` (המשתמש המחובר) — `decide()`, `mayActAlone(scope)` (כעת לפי הפרופיל), `isDenied()`;
מתעדכן ממשיכת העובדים (שינוי תפקיד בדשבורד נקלט בלי התנתקות).

**"אסור"**: הכפתור מוסתר או מוצג ולחיצה מסבירה — לפי הפרמטר `permissionsDeniedUi` ("הסתר" / "הצג מושבת עם

אוסר — אין עקיפה.

**"דורש אישור"**: `PermissionGate` (shell) מציג את חלון ה-PIN המקומי עם המאשרים האפשריים בלבד; אחרי אישור
הפעולה רצה פעם אחת, והאישור (או הסירוב) נרשם ב-audit (`category = permission`).

### 6.3 Offline

הפרופיל של כל עובד וה-hash של ה-PIN שמורים בקופה ⇒ החלטה ואישור מנהל זהים עם רשת ובלי. ה-audit נכתב
מקומית ונשלח מה-outbox עם id ייחודי (`kind:entityId`) — שליחה חוזרת היא אותה שורה בענן. אין "מצב
Offline" שמדלג על בדיקה.

### 6.4 `CashDrawerService.requestOpen()` — מיפוי לאפיון המגירה

| §19 שלב | מימוש |
|---|---|
| זיהוי משתמש | `OperatorSession`; בלי משתמש — רק בדיקת חומרה של טכנאי (קוד טכנאי) |
| תפקיד והרשאה | `CashDrawerPolicy.evaluate` — ההרשאה לפי ההקשר (`DrawerContext`) |
| הקשר וסיבה | פתיחה ידנית דורשת סיבה (פרמטר), "אחר" דורש הערה; Cash In/Out/הפקדה דורשים סכום |
| אימות עסקה/תשלום | `CASH_SALE` רק עם `saleId` של מכירה שנרשמה במזומן; `REFUND` עם הזיכוי |
| משמרת | בלי משמרת פתוחה ⇒ `AFTER_CLOSE`: חסום אם "אפשר פתיחה לאחר Z" כבוי, אחרת לפי `OPEN_AFTER_CLOSE` |
| מגבלות | מקסימום פתיחות ידניות למשמרת, סף אישור ל-Cash Out/הפקדה, "כל פתיחה ידנית באישור מנהל", סף התפקיד |
| Manager Override | `NeedsApproval` ⇒ חלון PIN; המאשר חייב לכסות את הסכום ולהחזיק `APPROVE_OPEN` |
| יצירת Audit | שורה `pending` ב-`drawer_events` **לפני** הפקודה |
| פקודה פיזית | `kick` — מוחזק רק על ידי השירות (`AppContainer.kickDrawer` פרטי) |
| שמירת Result | `approved` / `failed` + שליחה לענן; חסימה ⇒ `denied`, בלי פקודה |

כל המסלולים: סיום תשלום מזומן (כולל פיצול — רק כשיש רכיב מזומן, §12), "פתח מגירה" עם סיבות, הכנסה /
הוצאה / הפקדה / ספירה, בדיקת חומרה (אבחון), החזר מזומן (קופה והיסטוריה, §13), ואחרי Z. בדיקת קוד מקור
בבדיקות מוודאת שאין קריאה לפקודת המגירה מחוץ לשירות.

### 6.5 תנועות, יתרה צפויה, ספירה

* `cash_movements`: `cash_in` / `cash_out` / `deposit` / `count` — עם `expectedBefore` / `expectedAfter`
  (snapshot, §8), מי, מי אישר, ופתיחת המגירה המקושרת (שתי ישויות, §7).
* **יתרה צפויה** (§8): קרן פתיחה + מכירות מזומן (נטו מהחזרים) + טיפים במזומן + Cash In − Cash Out − הפקדות.
  ה-X של הקופה כולל את התנועות ב"מזומן צפוי" (ולכן גם הפער בסגירה), בלי לגעת במחזור.
* **ספירה**: "ספירת מגירה" פותחת את המגירה (COUNT / BLIND_COUNT), מקבלת את הסכום, מציגה צפוי / נספר / פער.
  **Blind Count** (פרמטר): היתרה הצפויה לא מוצגת לפני הזנת הסכום — במסך הספירה, ב-X הביניים (במסך
  ובנייר), בכרטיס סגירת המשמרת ובשלב הספירה של "הפק Z"; כל ספירה בסגירת משמרת / Z נרשמת כתנועת `count`
  (מי ספר, הצפוי, הפער). ה-X שבסגירה (אחרי הספירה) מציג צפוי, נספר ופער.

### 6.6 חריגות (§10–§11)

`server/app/services/cash_drawer_exceptions.py` — טבלה קטנה של סוגי החריגות, כתובים כשורות
`audit_exceptions` (עם `till_event_id` = האירוע) דרך ה-Detector הקיים:

| סוג | מתי | ספים (פרמטרי מגירה) |
|---|---|---|
| `drawer_after_close` | פתיחה לאחר סגירה / Z | — |
| `drawer_manual_burst` | X פתיחות ידניות של אותו עובד בתוך Y דקות | `alertOpensCount`, `alertOpensWithinMinutes` |
| `drawer_manual_over_max` | מעל מקסימום פתיחות ידניות במשמרת | `maxManualOpensPerShift` |
| `cash_out_over_threshold` | Cash Out מעל הסף | `cashOutAlertAmount` |
| `drawer_count_variance` | ספירה עם פער מעל הסף | `varianceAlertAmount` |
| `drawer_open_near_variance` | פתיחה ידנית בדקות שלפני ספירה עם פער | `nearVarianceMinutes` |
| `drawer_open_no_reason` | פתיחה ידנית בלי סיבה / "אחר" בלי הערה כשנדרש | — |
| `drawer_open_denied` | ניסיון חסום | — |

ובנוסף, כל פתיחה ידנית מאושרת היא החריגה הקיימת `drawer_open` ("פתיחת מגירה ללא מכירה").

**"יומן חריגות" והתראות SMS**: קטלוג היומן (`app/services/exception_alerts/catalog.py`, `KINDS`) מצרף את כל
`DRAWER_EXCEPTION_KINDS`, כך שכל חריגת מגירה נרשמת ביומן משורת ה-`audit_exceptions` שלה (מקור `audit_exception`),
עם שמה בעברית ורמת החומרה, וניתן לבחור אותה בחוק התראת SMS ("התראות SMS על חריגות").

### 6.7 פרמטרי ניהול (§17)

ירושה: חברה → סניף → נקודת מכירה → קופה (פרמטרי קופה). "פתיחה אוטומטית במכירת מזומן" ו"אפשר פתיחה ידנית" הם
הפרמטר הקיים `cashDrawer` (כבוי / בתשלום מזומן / + כפתור פתיחה). השאר: `cashDrawer.requireReason`,
`requireNoteForOther`, `requireManagerApproval`, `cashMovementsEnabled`, `cashOutApprovalAmount`,
`allowOpenAfterClose`, `blindCount`, `maxManualOpensPerShift`, `alertOpensCount`, `alertOpensWithinMinutes`,
`cashOutAlertAmount`, `varianceAlertAmount`, `nearVarianceMinutes`, ו-`permissionsDeniedUi`.

## 9. פתוח / החלטות

* סף `REFUND.maxAmount` נאכף בכתיבת הזיכוי (סל ו-היסטוריה); כניסה למצב החזרה עדיין לפי ההרשאה בלבד (הסכום לא ידוע שם).
* מאשר שמקליד קוד מנהל (ElevationSheet, שם משתמש מוקלד) כפוף למגבלות התפקיד שלו: כשיש סכום / אחוז והמאשר
  הוא עובד קופה ברשימת הקופה, האישור שהענן נתן נבדק מול התפקיד שלו, ואם אינו מכסה — לא משמש ומוחזר לענן מיד.
  משתמש ענן ללא כניסה לקופה אין לו תפקיד קופה — בדיקת התפקיד בענן קובעת.
* אמצעי זיהוי נוספים למאשר (כרטיס / NFC / QR) — אותו מסלול, PIN בלבד כרגע.
* עובד קופה **חדש** בלי תפקיד שנבחר מקבל את "קופאי" של האפיון (מי שנוצר כמנהל חנות — "מנהל" של האפיון, כדי
  שהתפקיד בטופס והתפקיד בקופה לא יסתרו); יצירת העובד יוצרת את תפקידי החברה אם טרם נוצרו, והעובדים הקיימים
  נשארים ב"הרשאות קודמות". ניתן להחליף ל"קופאי (הרשאות קודמות)". המשתמש "default" שנוצר אוטומטית לסניף חדש
  נשאר כמות שהוא (מנהל, "הרשאות קודמות").
* בדיקת חומרה מהמסך הטכני כשעובד מחובר נבדקת לפי `OPEN_FOR_TEST` שלו (קוד טכנאי לבדו — רק כשאיש לא מחובר).
