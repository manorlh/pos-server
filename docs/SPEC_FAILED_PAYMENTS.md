# עסקאות שלא הושלמו — ניסיונות תשלום שנכשלו — אפיון

> מקור: תלונת הבעלים (07.10.2026): "בדוח משמרת — עשינו עסקה שלא עברה על סה״כ של 140 ש״ח, בפועל היא לא עברה, למה הוא לא מדווח?"
> קוד בענן: `server/app/models/failed_payment.py`, `server/app/services/failed_payments.py`, `server/app/routers/failed_payments.py`, `server/app/schemas/failed_payment.py`, מיגרציה `5d9e1f3a7c62`. דשבורד: `client/src/components/dashboard/failed-payments/`, `client/src/lib/failedPayments.ts`. בדיקות: `server/tests/test_failed_payments.py`, `client/src/lib/failedPayments.test.ts`.
> קשור: [SPEC_CARD_RECOVERY.md](SPEC_CARD_RECOVERY.md) (תשובת אשראי לא ידועה — מתי ניסיון נחשב "לא חויב"), [SPEC_TRAINING_MODE.md](SPEC_TRAINING_MODE.md).

## 1. הבעיה

תשלום שנכשל במסוף — כרטיס שנדחה, ביטול במסוף או ע״י הקופאי, מסוף שלא ענה (והבירור הכריע "לא חויב"), תקלת מסוף, אשראי נעול — **לא מפיק מסמך מס**. לכן אף דוח לא הראה אותו: לא דוח המשמרת, לא X, לא Z, לא הדשבורד. הבעלים רואה בקופה שהלקוח ניסה לשלם ₪140 ונכשל, ובדוחות אין לזה זכר.

בנוסף: מכירה באשראי שנדחתה משאירה בענן מסמך במצב `cancelled` (למשל ₪79 היום) — ואף תצוגת משמרת / Z לא מציגה אותו.

**העיקרון:** הכול **מידע בלבד**. שום דבר כאן לא נכנס לסה״כ המכירות, לתקבולים, למע״מ, ל-Z, לייצוא לרו״ח או לשידור. כל סכום פיסקלי נשאר בדיוק כפי שהיה.

## 2. מה הקופה רושמת

**שורה אחת לכל ניסיון = vuid אחד.** ניסיון חוזר / בירור (SPEC_CARD_RECOVERY §3) של אותו vuid מעדכן את **אותה** שורה (התוצאה הסופית, זמן ההכרעה) — לא שורה חדשה.

- **כשלים לפני שהמסגרת יצאה למסוף** (נעילת אשראי, מסוף לא מוכן) באותה קופה ובאותו סל, באותו סכום ובאותה תוצאה — **מתאחדים לשורה אחת** (קופאי שלוחץ "אשראי" חמש פעמים על מסוף נעול הוא ניסיון אחד, לא חמישה).
- **קישור לתשלום שהצליח:** כשאותו סל משולם בהמשך (במזומן, באשראי, בשובר, מעורב), הקופה מעדכנת את הניסיון במסמך ששילם (`paidByTransactionId`), באמצעי (`paidByMethod`) ובזמן (`paidAt`), ושולחת אותו שוב **עם אותו id**.
- **המסמך שבוטל:** כשנכתב מסמך `pending` לניסיון והקופה ביטלה אותו, מזההו נשמר ב-`transactionId` (הוא מגיע לענן כמסמך `cancelled` עם אותו id).

| שדה | משמעות |
|---|---|
| `id` | מזהה הניסיון בקופה (UUID), קבוע לאורך חייו |
| `occurredAt` / `resolvedAt` | תחילת הניסיון / הכרעת התוצאה הסופית (UTC) |
| `shiftId`, `businessDate` | המשמרת ויום העסקים של הקופה |
| `posUserId`, `employeeName` | הקופאי (כמו `cashierId` במסמכים) ושמו |
| `amountAgorot` | הסכום באגורות, תמיד חיובי |
| `method` | אמצעי התשלום (`card` היום; `voucher` ואחרים אפשריים) |
| `kind` | `sale` — מכירה · `keyed` — הקלדה ידנית · `payout` — החזר כספי לכרטיס (זיכוי) שנכשל |
| `channel` | `till` — קופה · `kiosk` — קיוסק |
| `terminalType`, `terminalId` | `agamento` / `nayax_lan` / `nayax_usb` / `zcredit` / `synqpay`, ומספר המסוף |
| `outcome` | התוצאה (§2.1) |
| `reasonCode`, `reasonMessage` | הקוד ומילות המסוף (עד 300 תווים) |
| `cardBrand`, `cardLast4` | המותג ו-4 הספרות האחרונות **בלבד** (§7) |
| `lineCount`, `vuid` | מספר השורות בסל, ה-vuid |
| `transactionId` | המסמך הממתין שבוטל (אם נכתב) |
| `paidByTransactionId`, `paidByMethod`, `paidAt` | המסמך ששילם את אותו סל בהמשך |
| `updatedAt` | השינוי האחרון של השורה **בקופה** |

### 2.1 תוצאות

| `outcome` | תווית |
|---|---|
| `declined` | נדחתה |
| `cancelled_terminal` | בוטלה במסוף |
| `cancelled_cashier` | בוטלה ע״י הקופאי |
| `no_answer` | אין תשובה מהמסוף — לא חויב |
| `terminal_error` | תקלת מסוף |
| `card_locked` | אשראי נעול |

תשובה שתוצאתה **עדיין לא ידועה** (SPEC_CARD_RECOVERY §4) אינה "נכשלה": היא נרשמת כאן רק כשהוכרעה כ"לא חויב" (`no_answer`). ניסיון שנמצא בבירור **מאושר** — אינו כאן (הוא מכירה).

## 3. בדוחות הקופה

בדוח המשמרת (X ביניים), ב-X של סגירת המשמרת, בהיסטוריית המשמרות (מסך והדפסה חוזרת) וב-Z של הקופה — **במסך תמיד, ועל הנייר רק כשהפרמטר `printFailedPaymentsWithReports` מופעל** (ברירת מחדל: כבוי; §3.2 — הדפסה נפרדת) — חלק, **אחרי** כל הנתונים של הדוח (אחרי המגירה והשידור), לעולם לא בתוכם:

```
עסקאות שלא הושלמו
מידע בלבד — לא נכלל בסה״כ המכירות
מספר / סה״כ                 2 / ₪219.00
14:32 נדחתה (קוד 4)             ₪140.00
  אשראי · ויזה ****1234
  שולם בהמשך במזומן
14:41 ללא מענה, לא חויב          ₪79.00
  אשראי · ****5678
זיכויים שלא הושלמו            1 / ₪70.00
14:50 בוטלה במסוף                ₪70.00
  זיכוי לכרטיס · ****1234
מכירות שבוטלו
מספר / סה״כ                  1 / ₪79.00
13:10 · מסמך 20000057            ₪79.00
```

- הנייר של הקופה הוא 58 מ״מ (384 נקודות): לכל ניסיון שורה של "שעה + תוצאה (+ קוד המסוף)" והסכום, שורה של אמצעי · מותג ****1234 (· "קיוסק" כשהניסיון מהקיוסק), ושורה "שולם בהמשך במזומן / באשראי / בשובר / (מעורב)" כשהסל שולם. על הנייר התוצאה בניסוח קצר ("ללא מענה, לא חויב", "בוטלה ע״י קופאי"); במסך — המלא, עם שם העובד ומילות המסוף.
- ניסיונות החזר לכרטיס (`payout`) — בשורה נפרדת "זיכויים שלא הושלמו: N / ₪X", **לא** בסה״כ של המכירות שלא הושלמו.
- "מספר / סה״כ" מודפס תמיד, גם `0 / ₪0.00` — כך רואים שאין כשלים (ולא שהחלק חסר). "זיכויים שלא הושלמו" ו"מכירות שבוטלו" (§6) — רק כשיש.
- ה-X נבנה מ-`shiftId` של הניסיונות; ה-Z של הקופה — מהחלון שלו (`periodStart` → `closedAt`; בלי `periodStart` — מסגירת ה-Z הקודם בקופה), מהרישום **של הקופה עצמה** (כולל ניסיונות שעדיין לא נשלחו לענן). אף נתון של ה-X / ה-Z לא משתנה בגללו.

**פרמטר קופה `printFailedPaymentsWithReports`** — "הדפסת עסקאות שלא הושלמו בדוח משמרת / Z" (בוליאני, **ברירת מחדל: כבוי** — הבעלים, 09.10.2026: "בקופה בהדפסת משמרת אל תדפיס את עסקאות שלא הושלמו, אפשר להדפיס בנפרד"). כבוי (וגם כשלא נקבע) — החלקים **לא מודפסים** ב-X, ב-X של הסגירה, בהדפסה חוזרת מההיסטוריה וב-Z של הקופה; מופעל ("true" / "כן" / 1 / yes / on) — מודפסים בסוף הדוח כמו קודם. במסך הקופה ובדשבורד הם מוצגים תמיד. רשום בענן כפרמטר מובנה (`FAILED_PAYMENTS_PARAMETER_SPECS` ב-`app/services/failed_payments.py`, נוסף ל-`BUILTIN_PARAMETERS`; נוצר בעליית השרת ע״י `ensure_builtin_parameters`), וניתן לקבוע אותו לפי חברה, סניף, נקודת מכירה או קופה. הוא מחליף את `printFailedPayments` ("הדפסת עסקאות שלא הושלמו בדוחות", מופעל כברירת מחדל): מיגרציה 9b4e2f7a1c58 מכבה את ההגדרה הישנה (`is_active = false`, הערכים נשמרים) והקופה כבר לא קוראת אותה.

**שום נתון לא משתנה:** הפרמטר קובע רק אם השורות האלה מצורפות לנייר. ה-X, ה-Z, המספרים, תוכן ה-Z בענן והסכומים — זהים עם הפרמטר ובלעדיו (בדיקות: `FailedPaymentsPrintTest` בקופה).

### 3.1 ה-Z של הענן על הנייר

ה-Z שהקופה מדפיסה מהענן (`GET /sync/{machine_id}/z-reports/{id}/print-document`) — וגם עותק ה-80 מ״מ בדשבורד (`GET /z-reports/{id}/print-document`, `GET /z-reports/print-documents`):

- **פירוט קופה של Z סניפי** (`?till=<machineId>`) — "עסקאות שלא הושלמו" ו"מכירות שבוטלו" **של אותה קופה**, שורה לכל ניסיון כמו בקופה (§3).
- **Z קופה** / Z על קופה אחת — אותו פירוט.
- **Z סניפי מלא על כמה קופות** — שורה לכל קופה ("קופה 2 — 3 / ₪215.00").
- **סיכום הסניף** (`?part=summary`) — בלי החלקים (נשאר קצר).

החלקים נוספים **אחרי** כל הבלוקים הפיסקליים ולפני הכותרת התחתונה, ונקראים **בזמן ההדפסה** (ניסיון שהגיע אחרי הפקת ה-Z יופיע בהדפסה הבאה) — שלא כמו שאר ה-Z, שנבנה רק ממה שנשמר בהפקה. כל חלק נושא `"key": "failed_payments"` / `"key": "cancelled_sales"` ו-`"informational": true` — הקופה מסירה אותם מהנייר כש-`printFailedPaymentsWithReports` כבוי (מפענח המסמך מתעלם משדות שאינו מכיר). תקלה בבניית החלקים לעולם לא מפילה את הדפסת ה-Z.

### 3.2 הדפסה נפרדת — "הדפס עסקאות שלא הושלמו"

בכל מסך בקופה שמציג את החלק — דוח המשמרת (X), סגירת משמרת, פירוט משמרת בהיסטוריית המשמרות ומסך ה-Z של הקופה אחרי ההפקה — כפתור **"הדפס עסקאות שלא הושלמו"** בתחתית הכרטיס. הוא מוצג רק כשיש לפחות שורה אחת (ניסיון שנכשל, זיכוי שלא הושלם או מכירה שבוטלה) ומדפיס **רק את החלק**, כפתק עצמאי, בלי קשר לפרמטר:

- כותרת: שם העסק, ח.פ. / ע.מ., סניף, אזור, "קופה N · שם" — כמו ב-X; "עסקאות שלא הושלמו"; ומה הפתק מכסה: "משמרת #N" או "Z מס׳ N".
- תאריך הנפקה, תאריך עסקים, והחלון: תחילת / סיום משמרת (משמרת פתוחה — "נכון לשעה"), או תחילת / סיום תקופה של ה-Z.
- אותן שורות בדיוק כמו בסוף הדוח (§3): "מידע בלבד", "מספר / סה״כ", כל ניסיון, "זיכויים שלא הושלמו", "מכירות שבוטלו" — בלי כפילות הכותרת.

אותו מצייר (`ReportRenderer`), אותו לוגו מסמך ואותה בחירת מדפסת לדוחות (`ReportPrinterChoice`) כמו ה-X וה-Z. לא נשמר, לא נשלח לענן, ולא נוגע בשום נתון.

## 4. החוזה (קופה → ענן)

`POST /api/v1/sync/{machine_id}/failed-payments` — אימות קופה בלבד (machine JWT), בדיוק כמו `POST /sync/{machine_id}/events`. גוף JSON ב-camelCase (השדות בטבלה ב-§2):

```json
{
  "id": "6f1c…", "occurredAt": "2026-10-07T11:32:05Z", "resolvedAt": "2026-10-07T11:32:41Z",
  "shiftId": "…", "businessDate": "2026-10-07", "posUserId": "…", "employeeName": "דנה",
  "amountAgorot": 14000, "method": "card", "kind": "sale", "channel": "till",
  "terminalType": "agamento", "terminalId": "0882001", "outcome": "declined",
  "reasonCode": "003", "reasonMessage": "התקשר לחברת האשראי",
  "cardBrand": "visa", "cardLast4": "1234", "lineCount": 3, "vuid": "…",
  "transactionId": null, "paidByTransactionId": null, "paidByMethod": null, "paidAt": null,
  "updatedAt": "2026-10-07T11:32:41Z"
}
```

| תשובה | מתי |
|---|---|
| 201 `{"id", "status": "accepted"}` | בפעם הראשונה |
| 200 `{"id", "status": "updated"}` | התוכן השתנה **ו-`updatedAt` אינו ישן מהשמור** — מוחל |
| 200 `{"id", "status": "duplicate"}` | אותו תוכן, או שליחה ישנה (`updatedAt` ישן) — **לא מוחל**: שליחה ישנה לעולם לא דורסת קישור חדש |
| 409 `failed_payment_id_conflict` | ה-id שייך לקופה אחרת |
| 409 `machine_not_assigned` | קופה בלי סניף |
| 422 | גוף לא תקין (תוצאה שאינה קוד, סכום שלילי, UUID שבור) |

הקופה מתייחסת ל-2xx ול-404/410 כנמסר, ומחנה 409 / 4xx קבוע. שדות שהענן אינו מכיר — מתעלמים. `kind` / `outcome` / `channel` / `method` הם קודים (אותיות קטנות, ספרות, `_`, עד 32) — ערך עתידי נשמר כמו שהוא ומוצג כקוד.

**מצב הדרכה:** הקופה רשאית לשלוח `"training": true`. ניסיון מסומן — או, כשהסניף במצב הדרכה, ניסיון של משמרת הדרכה או שמזכיר מסמך הדרכה — נשמר בהסגר (`training_documents`, `kind = other`) ולא בטבלה האמיתית, ונענה בדיוק כמו אמיתי. אחרי שהסניף יצא ממצב הדרכה — נזרק ונרשם ביומן (כמו אירועי הקופה, SPEC_TRAINING_MODE.md).

## 5. הטבלה

`failed_payment_attempts` (מיגרציה `5d9e1f3a7c62`, אידמפוטנטית — ה-API המקומי עשוי ליצור אותה לפני alembic):

`id` (מזהה הקופה, מפתח) · `tenant_id` · `company_id` · `shop_id` · `area_id` · `machine_id` · `shift_id` (בלי מפתח זר — סדר ההגעה משתנה, כמו `till_events`) · `business_date` · `pos_user_id` · `employee_name` · `occurred_at` · `resolved_at` · `amount_agorot` (BigInteger) · `method` · `kind` · `channel` · `terminal_type` · `terminal_id` · `outcome` · `reason_code` · `reason_message` (300) · `card_brand` · `card_last4` (4) · `line_count` · `vuid` · `transaction_id` · `paid_by_transaction_id` · `paid_by_method` · `paid_at` · `created_at` (קבלה ראשונה בענן) · `updated_at` (השינוי האחרון בקופה).

אינדקסים: `(tenant_id, occurred_at)`, `(machine_id, occurred_at)`, `shift_id`, `transaction_id`, `paid_by_transaction_id`.

## 6. מכירות שבוטלו

מסמכים במצב `cancelled` (למשל מכירה באשראי שנדחתה והקופה ביטלה את המסמך הממתין) — באותו היקף ובאותם מסננים — **שאף ניסיון לא מסביר**:

- לא ה-`transactionId` של ניסיון כלשהו, ו
- לא באותו סל (`basket_id`) כמו המסמך שבוטל או המסמך ששילם של ניסיון.

כך אותו כשל לעולם לא מופיע פעמיים (פעם כניסיון ופעם כמכירה שבוטלה). מוצגים: מספר המסמך כפי שהודפס (עם הקידומת), סכום (בשקלים כפי שנשמר + באגורות), זמן, קופה, וקופאי כשידוע. מכירה שבוטלה אינה בסה״כ — כמו תמיד.

## 7. פרטיות

מהכרטיס נשמרים **רק** 4 הספרות האחרונות והמותג. `cardLast4` שאינו בדיוק 4 ספרות — לא נשמר (null); מותג לא מוכר — `other`. אין בטבלה עמודה למספר כרטיס, תוקף, track או כל דבר אחר מהכרטיס, ושדות כאלה שנשלחים בטעות — נזרקים. `reasonMessage` נחתך ל-300 תווים.

## 8. הדשבורד

`GET /api/v1/failed-payments` — משתמש Clerk, היקף בדיוק כמו `GET /transactions` (`scope_query_by_user`; קופאי רואה מה שהוא רואה בעסקאות — הסניף שלו).

פרמטרים: `machineId`, `shopId`, `shiftId`, `zReportId`, `from`, `to` (ימים, כמו בעסקאות), `outcome` (רשימה מופרדת בפסיקים), `cardLast4`, `page`, `pageSize` (עד 500). בלי משמרת, Z או תאריכים — 30 הימים האחרונים, כמו העסקאות. `zReportId` — כל המשמרות שה-Z לקח (`shifts.z_report_id`), ולניסיון בלי משמרת: קופות ה-Z בחלון שלו; ב-Z סניפי — של כל הקופות (כל שורה נושאת שם קופה ומספר); עם `machineId` — קופה אחת שלו. Z שאינו של הדייר — 404.

```json
{
  "page": 1, "pageSize": 50, "total": 3,
  "summary": {"count": 2, "totalAgorot": 21900, "payoutCount": 1, "payoutTotalAgorot": 7000, "paidLaterCount": 1},
  "items": [{"…כל השדות…", "machineName": "בר", "posNumber": "2", "shopName": "…", "shiftNumber": 14,
             "transactionNumber": "20000057", "paidByTransactionNumber": "20000058", "receivedAt": "…"}],
  "cancelledSales": {"count": 1, "totalAgorot": 7900,
                     "items": [{"id": "…", "documentNumber": "20000061", "totalAmount": 79.0, "totalAgorot": 7900,
                                "createdAt": "…", "machineName": "…", "posNumber": "2", "cashierName": "…"}]}
}
```

`summary.count` / `totalAgorot` — מכירות (`sale` + `keyed`) בלבד; החזרים לכרטיס בנפרד; `paidLaterCount` — מכירות שהסל שלהן שולם בהמשך.

**תצוגות:**

- **עסקאות** — שבב "ניסיונות תשלום שנכשלו" בסינון אמצעי התשלום. נבחר — הדף מציג את הניסיונות (לפי הקופה / הסניף / התאריכים / 4 ספרות שבדף) בטבלה משלהם: זמן, קופה, עובד, סכום (+ "זיכוי לכרטיס" / "הקלדה ידנית" / "קיוסק"), אמצעי, תוצאה (+ קוד ומילות המסוף), מותג + ****1234, שורות, "שולם בהמשך ב…" עם קישור למסמך ששילם, והמסמך שבוטל. מעליה — "מידע בלבד" והסיכום; מתחתיה — "מכירות שבוטלו".
- **משמרת (X)** — חלק "עסקאות שלא הושלמו" (מסומן "מידע בלבד", לא בסה״כ): מספר / סה״כ, השורות, זיכויים שלא הושלמו, ו"מכירות שבוטלו".
- **Z** — אותו חלק בכרטיס של כל קופה.
- אין כלום — לא מוצג כלום.

## 9. צד הקופה (Android)

**קבצים** (`pos-android/app/src/main/java/il/co/runnersys/pos/`):

- `data/local/FailedPaymentEntities.kt` — טבלת Room `failed_payment_attempts` (שורה לכל ניסיון), ה-DAO, והמיגרציה 33 → 34 (`FailedPaymentMigration`, דרך `IdempotentSql`).
- `data/repo/FailedPaymentRecorder.kt` — המקליט: רישום, עדכון לפי vuid, איחוד כשלים לפני המסוף, קישור לתשלום שהצליח, שמירה 62 יום, והתור לענן.
- `ui/checkout/CheckoutFailedPayments.kt` — נקודות החיבור בקופה (`CheckoutViewModel`: שורה אחת בכל מקום שתשלום נכשל או שהסל שולם).
- `domain/FailedPayments.kt` — משמעות תשובת המסוף, המילים, ושורות הדוח (נייר ומסך).
- `ui/reports/FailedPaymentsUi.kt` — החלק במסכים, על הנייר, הפרמטר `printFailedPaymentsWithReports`, וכפתור ההדפסה הנפרדת (§3.2); הפתק עצמו — `failedPaymentsSlipLines` ב-`hardware/printer/ReportRenderer.kt`.
- `data/remote/FailedPaymentDtos.kt` — גוף ה-`POST`.

**מאגר השחזור לא מספיק:** `card_attempts` (SPEC_CARD_RECOVERY) מחזיק ניסיון רק עד שהוכרע ומוחק אותו — לכן טבלה משלו.

**מתי נרשם ניסיון** (תמיד ברקע, על worker יחיד ובסדר — מסך התשלום לא מחכה לו ולא נכשל בגללו):

| מה קרה | `outcome` |
|---|---|
| המסוף ענה "לא" לעסקה עצמה (דחייה, כרטיס, קוד) | `declined` + קוד ומילות המסוף |
| ביטול על מסך המסוף (126/998) | `cancelled_terminal` |
| הקופאי לחץ "ביטול" (או "ויתור" עם מזומן במגירה) כשהמסגרת בדרך, והתשובה ביטול / שתיקה / "לא נמצא" | `cancelled_cashier` (דחייה שהגיעה בכל זאת — `declined`) |
| הקופאי ביטל לפני שהמסגרת יצאה, והמסמך הממתין בוטל | `cancelled_cashier` עם `transactionId` |
| תשובה שאבדה, ובבירור לפי vuid: "לא נמצא", או "בוטלה" (הביטול שלנו אחרי השתיקה) | `no_answer` |
| תשובה שאבדה, ובבירור: נדחתה | `declined` |
| "סמן כלא אושר" של מנהל (לא "סמן כטופל" על אשראי שאושר) | `no_answer` |
| השחזור אחרי נפילת התהליך (`CardAttemptRecovery`) — לא חויב | כמו בבירור |
| מסוף תפוס / vuid כפול (-1 / -5 / 995) | `terminal_error` |
| המסוף לא זמין / אין כתובת / TweezerComm כבוי — לפני כל מסגרת | `terminal_error` |
| נעילת אשראי (CardLock) | `card_locked` |

זיכוי לכרטיס מתוך סל עם החזרות (`payoutCard`) נרשם כ-`kind = payout`.

**שורה אחת לניסיון:** אותו vuid מעדכן את אותה שורה (התוצאה האחרונה, הזמן הראשון נשמר). כשל לפני המסוף באותה עגלה, אותו סכום, אותה תוצאה ואותו סוג — מעדכן את השורה הקודמת ולא מוסיף.

**הקישור לתשלום שהצליח:** הסל הוא מזהה העגלה (`Cart.id`) — זהה גם כשהקופאי חוזר לעגלה ופותח שוב את מסך התשלום. כשמסמך נכתב והמסך עובר ל"הושלם" (מזומן, אשראי, סל) — כל הניסיונות של אותה עגלה שעוד לא קושרו מקבלים `paidByTransactionId`, `paidByMethod` (מתוך רגלי התשלום: `cash` / `card` / `voucher` / `mixed`) ו-`paidAt`. ניסיון שהוכרע אחרי שהמכירה שולמה באמצעי אחר ("אמצעי אחר" כשהאשראי לא ידוע) — מקושר מיד ל-`supersededBy` שלו.

**שליחה:** כל שינוי נכנס ל-outbox כשורה מסוג `failed_payment` עם גוף מלא (המצב באותו רגע; מזהה השורה `failed-payment:<id>:<updatedAt>`), נשלח לצד התור (`SIDE_KINDS`, לא מחכה לסדר המשמרות) ומיד (`flushSide`). 2xx / 404 / 410 — נמסר; 409 — מוחנה. `sessionKey` לא נשלח.

**בנייר:** `printFailedPaymentsWithReports` כבוי (ברירת המחדל) — החלקים לא מודפסים ב-X, בסגירה וב-Z של הקופה, וגם החלקים שהענן מסמן ב-`key` (`failed_payments`, `cancelled_sales`) מוסרים מ-Z הענן לפני ההדפסה (`PrintSection.key`). במסך — תמיד, עם הכפתור "הדפס עסקאות שלא הושלמו" (§3.2).

**Z סניפי מקומי (LAN):** מדפיס שורת סיכום לכל קופה ולא פירוט קופה — לכן אין בו את החלק.

**לא נרשם:** זיכוי לכרטיס מתוך היסטוריית המסמכים (`DetailViewModel`) — רק תשלומים במסך התשלום (כולל זיכוי לכרטיס בסל); וקיוסק בלי מסוף חיצוני מוגדר (הגדרה, לא ניסיון).
