# עדכוני גרסה — אנדרואיד ו-Windows, והאפליקציה המודולרית ל-Windows

גרסה 1.0 · 07.10.2026 · ענף `feat/r2m-pos-2026-10`

> משלים את `docs/SPEC_DEVICE_ROLE_MODEL.md` (סוג מכשיר, פלטפורמה, מכשירים לא-קופתיים), `docs/SPEC_KIOSK.md` (הקיוסק),
> `docs/SPEC_KDS.md` (מסכי מטבח ומסך איסוף) ו-`kiosk-desktop/README.md` (האפליקציה ל-Windows).

## 1. הבקשה ותשובה קצרה

הבעלים: "את ההתקנה שעשית ב-WEB יכולה להתאים גם לקופת ווינדוס, אז תהפוך אותה למודולרית. תחשוב על עדכונים איך זה קורה, כי עכשיו
צריך גם ווינדוס וגם אנדרואיד. האם עדכונים יורדים אוטומטית?" ובהמשך: "ההתקנה של הווינדוס יכולה לכלול KDS, קופה, קיוסק, מסך
מוכן/לא מוכן, וההגדרה מה הוא יהיה בהוספת מכשיר בענן במהלך הצימוד. חשוב מאוד: מכשירים KDS ומסך מוכן/לא מוכן אינם מערכות קופה
וחשבונאיות."

**האם עדכונים יורדים אוטומטית? כן — בשתי הפלטפורמות ההורדה תמיד אוטומטית וברקע; ההתקנה אוטומטית לפי השיוך:**

| | הורדה | התקנה |
|---|---|---|
| **אנדרואיד** | בכל סנכרון (`CloudSync` ← `AppUpdateRepository.check`), ברקע, עם בדיקת SHA-256 | שיוך "התקנה אוטומטית": כשהקופה סגורה (אין משמרת), או במשמרת פתוחה כשהקופה שקטה 2 דק׳ (אין סל, תשלום או שולחן). אחרת מהתפריט. **שקטה** באנדרואיד 12+ ובכל מכשיר שהאפליקציה בו device owner; **דורשת לחיצה** באנדרואיד 10/11 (ה-F20) — §5 |
| **Windows** | בהפעלה (אחרי דקה), כל 15 דק׳ ו"בדוק עכשיו", ברקע, עם בדיקת SHA-256 וגודל | שיוך "התקנה אוטומטית": כשהמכשיר פנוי (קיוסק במסך פתיחה / סגור, בלי הזמנה ובלי תשלום), ואם הוגדר חלון — רק בתוכו (למשל 02:00–05:00). תמיד שקטה (`/S`), והאפליקציה עולה מחדש לבד. "התקן עכשיו" בטכנאי — בכל זמן חוץ מבזמן הזמנה/תשלום |

בלי "התקנה אוטומטית" בשיוך — הגרסה יורדת ומחכה ל"התקן עכשיו" (טכנאי ב-Windows, תפריט בקופה).

## 2. מסך אחד בדשבורד — "עדכוני גרסה"

`/dashboard/app-updates` (סופר-אדמין; טבלת הפריסה גם למנהלי מכונות של הארגון):

- **מתג פלטפורמה** (הכל / אנדרואיד / Windows) מעל הכול.
- **גרסאות:** העלאה — בוחרים פלטפורמה; אנדרואיד: APK (הגרסה נקראת מה-manifest); Windows: `R2M-POS-Windows-<גרסה>-setup.exe`
  (הגרסה משם הקובץ או מוקלדת; versionCode מחושב `a·1,000,000 + b·1,000 + c`). הערות. הענן מחשב SHA-256 וגודל. הוצאה משימוש (`isActive`).
- **שליחה (שיוך):** גרסה → ארגון / חברה / סניף / נקודת מכירה / מכשיר אחד, "התקנה אוטומטית", **אחוז פריסה** (פריסה מדורגת), ול-Windows
  גם **"אפשר חזרה לגרסה קודמת"** ו**חלון התקנה**.
- **שיוכים פעילים:** פלטפורמה, אחוז (ניתן לשינוי במקום), חלון, ביטול.
- **פריסה:** כל מכשיר — פלטפורמה, תפקיד (קופה / קיוסק / מסך מטבח / מסך מוכן), הגרסה שהוא מריץ (מה-heartbeat), גרסת היעד ומאיזו
  רמה, הסטטוס האחרון שדיווח (מוריד / הורד / מתקין / הותקן / נכשל + סיבה / נדחה), **מי מפגר** (מסנן "רק מכשירים שמפגרים" וספירה לכל פלטפורמה).

## 3. בענן — גרסאות, שיוכים, פריסה מדורגת, חזרה לגרסה

- `app_releases.platform` = `android` | `windows` (ברירת מחדל `android` — כל מה שהיה). שם גרסה ייחודי **בתוך פלטפורמה**.
- **שיוך וקדימות — אותם כללים, לכל פלטפורמה בנפרד:** מכשיר → נקודת מכירה → סניף → חברה → ארגון; ברמה אחת — החדש. שיוך למכשיר
  גובר על שיוך לסניף. שיוכי אנדרואיד ו-Windows לא משפיעים זה על זה (קיוסק Windows וקופת אנדרואיד באותו סניף מקבלים כל אחד את שלו).
  פלטפורמת המכשיר: הפרמטר `platform` בבקשה (בלי — `android`, כמו הקופה היום; ערך אחר — `422 invalid_platform`); בטבלת הפריסה —
  `device_info.platform` מהצימוד; בהורדה — הפלטפורמה של הגרסה המבוקשת (המכשיר מקבל את הקובץ רק אם זו הגרסה שהוא מקבל עכשיו בפלטפורמה הזו).
- **פריסה מדורגת:** לשיוך יש אחוז (1–100). מכשיר בשלב אם `sha256("<assignment>:<machine>") mod 100 < אחוז` — קבוע, ולכן הגדלת האחוז
  משאירה את מי שכבר בפנים. מכשיר מחוץ לשלב מדלג על השיוך וממשיך בסדר הרגיל — כך שיוך ישן באותה רמה ממשיך להחזיק את שאר הסניף בגרסה הקודמת.
- **חזרה לגרסה קודמת (rollback):** Windows — שיוך של גרסה ישנה עם "אפשר חזרה" (`allowDowngrade`): המכשיר מקבל versionCode נמוך יותר
  (לעולם לא את אותה גרסה), והמתקין של NSIS מתקין אותה מעל. **אנדרואיד — לא אפשרי:** אנדרואיד לא מתקין versionCode נמוך בלי הסרה
  (= מחיקת המסד המקומי, מסמכים ומונים). "חזרה" באנדרואיד = לבנות את הקוד הישן מחדש עם versionCode גבוה יותר (ה-versionCode הוא מספר
  ה-commits) ולשלוח אותו כגרסה חדשה. הענן מסרב ל-`allowDowngrade` על גרסת אנדרואיד. הוצאה משימוש של גרסה פגומה מחזירה את המכשירים
  לשיוך הבא שחל עליהם, אבל לא מורידה אותם — לשם כך צריך rollback.
- **הורדה:** רק הגרסה שהמכשיר מקבל עכשיו (`404` לכל אחרת), בטוקן של המכשיר.

| נקודת קצה | |
|---|---|
| `POST /app-releases` | multipart: `file`, `platform` (`android`/`windows`), `versionName`, `versionCode` (אנדרואיד, אם לא נקרא), `notes`. Windows: קובץ שמתחיל ב-`MZ` (אחרת `422 invalid_installer`), גרסה מהטופס או משם הקובץ (`422 windows_version_required` / `windows_version_invalid`), versionCode מוקלד שלא מתאים — `422 version_code_mismatch`; `409 app_release_version_taken` רק באותה פלטפורמה |
| `GET /app-releases?platform=` | הגרסאות, + `platform` |
| `POST /app-releases/{id}/assignments` | `level`, `targetId`, `autoInstall`, `rolloutPercent` (1–100, ברירת מחדל 100), `allowDowngrade` (אנדרואיד: `422 downgrade_not_supported_on_android`), `installWindow: {start, end}` ("HH:MM"; `422 install_window_invalid`). `machineCount` — מכשירי הפלטפורמה של הגרסה |
| `PATCH /app-release-assignments/{id}` | שינוי `rolloutPercent` / `autoInstall` / `installWindow` (`null` מוחק); שיוך מבוטל — `409 app_release_assignment_cancelled` |
| `GET /app-releases/rollout?platform=` | שורה לכל מכשיר: `platform`, `deviceRole`, `currentVersion`, `targetVersion`, `status` (+ הודעה), `behind`, `newestVersion`, `behindNewest` |
| `GET /sync/{m}/app-update?versionCode=&versionName=[&platform=windows]` | ההצעה: כל המפתחות תמיד, + `platform`, `allowDowngrade`, `rolloutPercent`, `installWindow` |
| `GET /sync/{m}/app-update/{id}/apk` (וגם `/file`) | הקובץ — APK או מתקין Windows |
| `POST /sync/{m}/app-update/status` | `downloading` / `downloaded` / `installing` / `installed` / `failed` / `declined` + `message` |

## 4. Windows — "R2M POS ל-Windows", אפליקציה מודולרית אחת

### 4.1 מבנה

מעטפת אחת (`kiosk-desktop/src/main/index.ts`), שכבת שירות משותפת אחת, ומודולים לפי תפקיד:

| שכבה | מה | קבצים |
|---|---|---|
| מעטפת | חלון מסך מלא, `kiosk://`, IPC, זהות ההתקנה | `src/main/index.ts`, `src/main/shell/identity.ts`, `src/preload` |
| שירות משותף | צימוד, הרשאה (טוקן מכונה מוצפן DPAPI), סנכרון, מטמון מדיה, הדפסה (SNBC / ESC-POS RAW ל-spooler או TCP 9100), ספקי תשלום (Nayax LAN, SynqPay), יומנים, טכנאי | `src/main/service.ts`, `sync/`, `media/`, `printer/`, `payment/`, `db/` |
| עדכונים | בדיקה, הורדה, אימות, התקנה, דיווח | `src/main/update/updater.ts`, `src/core/updatePolicy.ts` |
| תפקיד | איזה תפקיד, איזה מודול רץ | `src/core/roles.ts`, `src/main/roles/manager.ts` |
| קיוסק | הקיוסק של היום — ללא שינוי בהתנהגות | השירות + `src/renderer/kiosk` |
| מסך מטבח (KDS) | הלוח והפעולות של מכשיר KDS (תחנה / אקספו / מנהל) | `src/main/roles/kds.ts`, `src/core/kdsBoard.ts`, `src/renderer/roles/kds` |
| מסך מוכן / לא מוכן | מספרי איסוף בהכנה / מוכנים, צליל והבהוב, עובד מהמידע האחרון בלי אינטרנט | `src/main/roles/board.ts`, `src/core/pickupBoard.ts`, `src/renderer/roles/board` |
| קופה, מסך לקוח | פיגום בלבד: גבול מודול, ניתוב, מסך "תפקיד זה יגיע בגרסה הבאה" | `src/renderer/roles/RolePlaceholder.tsx` |

### 4.2 איך נבחר התפקיד — רק בענן

1. בדשבורד, "הוספת מכשיר": סוג מכשיר (קופה / קיוסק / מסך מטבח / מסך מוכן-לא מוכן) + פלטפורמה (Android / Windows) + סניף.
2. במחשב: כתובת שרת + קוד. **אין בחירת תפקיד במחשב**; מסך הטכנאי מציג את התפקיד לקריאה בלבד.
3. אחרי הצימוד: `machines/me` → `deviceRole`. קיוסק פעיל (`kiosk/sync` → `kiosk: true`) תמיד קיוסק. מכשיר שהוגדר מעמוד מסכי המטבח
   (`kds/device`; `pickup` = מסך מוכן) — כמו בקופה, השאלה נשאלת רק למסך או לקופה עם הפרמטר `kdsScreen`.
4. מסך מטבח ומסך מוכן **אינם קופה**: `machines/me` מחזיר להם `fiscal: false` (וזה גובר על כל דבר אחר במחשב —
   `src/main/roles/manager.ts` `fiscalOf`). אז השירות לא טוען מסופון בכלל, לא פותח משמרת, לא מריץ סגירה / Z אוטומטיים, `startPayment`
   נדחה, וה-heartbeat יוצא בלי עובדות Z. המסך משתמש רק בנקודות הקצה הפתוחות למסכים (heartbeat, `machines/me`, הגדרות / פרמטרים /
   קטלוג, `kiosk/sync`, `kds/device`, `kds/board`, `kds/actions`, עדכוני אפליקציה). גם הענן אוכף (`403 device_not_fiscal`) —
   `docs/SPEC_DEVICE_ROLE_MODEL.md` §2.2.
5. בצימוד המחשב שולח `device_info.platform: "windows"`; קוד שנוצר לאנדרואיד נדחה (`422 platform_mismatch`) ומסך הצימוד מציג את המשפט
   של הענן כפי שהוא ("קוד הצימוד נוצר למכשיר Android… צרו קוד חדש").

### 4.3 זהות ההתקנה (החלטות)

- `appId` = `il.co.runnersys.kiosk` — **נשאר**. NSIS מזהה את ההתקנה לפיו; appId חדש היה מתקין אפליקציה שנייה ליד כל קיוסק במקום לעדכן.
- `productName` = `R2M Kiosk` — **נשאר** (שם ה-exe ותיקיית ההתקנה). תיקיית הנתונים `%APPDATA%\R2M Kiosk` **נעוצה בקוד**
  (`app.setPath('userData')`) — בה הטוקן, המונים, המשמרות וה-Zים — ולכן שינוי שם מוצר בעתיד בטוח.
- מה שרואים: כותרת החלון, מסך הצימוד, הקיצור ("R2M POS") וקובץ ההתקנה `R2M-POS-Windows-<גרסה>-setup.exe`.
- **התקנה למשתמש (per-user)** מ-0.2.0: בלי הרשאות מנהל, ולכן עדכון שקט אמיתי תחת משתמש הקיוסק. מתקינים כשמחוברים כמשתמש הקיוסק.
- **מעבר מ-0.1.0** (הותקנה למחשב, עדכון ידני בלבד): משייכים 0.2.0, ובמסך הטכנאי של 0.1.0 לוחצים "התקן עכשיו" פעם אחת. 0.2.0
  נכנסת להתקנה למשתמש עם אותה תיקיית נתונים; את ההתקנה הישנה מסירים פעם אחת (מנהל) — הנתונים נשארים.

### 4.4 זרימת העדכון

1. **בדיקה** — בהפעלה (אחרי דקה), כל 15 דק׳ (`updateCheckMinutes` ב-`%APPDATA%\R2M Kiosk\kiosk.json`), "בדוק עכשיו". רק הצעה
   `platform: "windows"`, עם מזהה ו-SHA-256, לא הגרסה שרצה, ולא נמוכה יותר אלא אם rollback.
2. **הורדה ברקע** ל-`%APPDATA%\R2M Kiosk\updates\<release>.exe.part`, עם גיבוב בזמן ההורדה; גודל + SHA-256 + כותרת `MZ` — או שהקובץ נמחק
   ו-`failed` מדווח. כישלונות חוזרים: המתנה של 1, 2, 4… דק׳ (עד שעה). גרסה מוכנה נשמרת גם אחרי הפעלה מחדש.
3. **התקנה** — רק לשיוך "התקנה אוטומטית", כשמותר:
   - **לעולם לא** בזמן הזמנה או תשלום: לא במסכי הזמנה/תשלום/הצלחה, לא עם בקשה במסופון, לא עם תשלום שממתין לבירור;
   - קיוסק — אחרי דקה בלי שינוי במסך; מסך מטבח — 3 דק׳ בלי נגיעה; מסך מוכן — מיד;
   - אם בשיוך (או ב-`updateWindow` של kiosk.json) יש חלון — רק בתוכו (חלון יכול לחצות חצות).
   - "התקן עכשיו" (טכנאי) — בלי חלון ובלי המתנה, **אבל לא בזמן תשלום** (נבדק גם בשירות וגם במעדכן).
   לפני ההרצה הקובץ מגובב שוב; `installing` מדווח; NSIS רץ `/S --force-run` (שקט, מחליף, מפעיל מחדש) והאפליקציה נסגרת.
4. **אחרי ההפעלה** — הגרסה שרצה מושווית לזו שהותקנה: `installed`, או `failed` עם "ההתקנה לא הושלמה: רצה X במקום Y" (אחרי 15 דק׳).
5. **מסך הטכנאי** (קיוסק: שש נגיעות בפינה + קוד; מסך מטבח / מסך מוכן / פיגום — אותה מחווה): גרסה, מצב (מוריד X%, מוכן להתקנה,
   ממתין לחלון 02:00–05:00, נכשל + סיבה), מדיניות ההתקנה, "בדוק עכשיו" / "התקן עכשיו".

### 4.5 בלי חתימת קוד (עדיין) — SmartScreen

- **התקנה ראשונה** מקובץ שהורד בדפדפן: SmartScreen מציג "Windows protected your PC" ← "More info" ← "Run anyway" (הקובץ מסומן
  mark-of-the-web ואין לו מוניטין של מפרסם חתום).
- **עדכונים אוטומטיים לא עוברים ב-SmartScreen**: האפליקציה מורידה בעצמה (לא דפדפן), אין mark-of-the-web. מה שמגן: HTTPS, טוקן המכונה,
  הורדה רק של הגרסה המשויכת, ו-SHA-256 שהענן חישב בהעלאה (נבדק פעמיים). Defender עדיין סורק.
- **Smart App Control** (Windows 11, התקנה נקייה) חוסם תוכנה לא חתומה בכלל — לכבות במכשירים עד שתהיה חתימה.
- **להמשך:** תעודת חתימת קוד (OV/EV, או Azure Trusted Signing) — electron-builder חותם בבנייה (`win.signtoolOptions` /
  `win.azureSignOptions`); אז אפשר גם לבדוק במעדכן שהמתקין חתום באותו מפרסם לפני ההרצה.

### 4.6 העלאה מסקריפט

```bash
cd kiosk-desktop && npm run dist
R2M_ADMIN_TOKEN=<טוקן סופר-אדמין> npm run publish:release -- --server https://api.example.com --notes "מה חדש" \
    [--assign shop:<uuid> --auto-install --percent 20 --window 02:00-05:00]
```

הטוקן: בדשבורד, DevTools ← `await window.Clerk.session.getToken()` (חי כדקה). הסקריפט משווה את ה-SHA-256 שהענן חישב לקובץ המקומי.

## 5. אנדרואיד — עדכון שקט, בעלות מכשיר (Device Owner) והגדרת המכשירים

הבעלים (07.10.2026): "אני רוצה שתעדכן ספריות לבד כשאנחנו מוסיפים פיצ'ר חדש, אני לא רוצה לבקש אישור מהאנדרואיד". התשובה: האפליקציה
כ**בעלת המכשיר** (device owner) מתקינה את העדכונים של עצמה בלי שום אישור, בכל גרסת אנדרואיד ובכל סוג מכשיר. מגדירים פעם אחת לכל מכשיר.

### 5.1 מתי שקט ומתי צריך לחיצה

| מכשיר | נתיב ההתקנה (`updatePath`) | לחיצה? |
|---|---|---|
| **בעלות מכשיר** (כל גרסה) | PackageInstaller session שה-device owner מגיש (`device_owner`) | **לא** — בלי אישור ובלי "התקנת אפליקציות לא מוכרות" |
| אנדרואיד 12+ (קיוסק HIT, טאבלט P18) | session עם `USER_ACTION_NOT_REQUIRED` (`self_update`) | **לא** — אחרי אישור חד-פעמי של "התקנת אפליקציות לא מוכרות" |
| Urovo (8.1) בלי בעלות מכשיר | `android.device.DeviceManager().installApplication` של ה-ROM, ברפלקציה (`urovo`) | **לא** — כשהמחלקה קיימת ב-ROM |
| PAX (8.1) בלי בעלות מכשיר | NeptuneLite `getDal().getSys().installApp`, ברפלקציה (`pax`) | **לא** — רק כשספריית PAX בתוך האפליקציה (ראו `hardware/pax`) |
| אנדרואיד 7.1–11 אחרת (F20, SUNMI T2) | `ACTION_INSTALL_PACKAGE` + FileProvider (`tap`) | **כן** — מסך האישור של אנדרואיד |

ההחלטה היא אחת, בקוד טהור: `pos-android domain/DeviceManagement.kt` (`SilentUpdatePolicy.route`), והיא גם מה שמדווח לענן. מתקין יצרן שנכשל
(או שאישר ולא החליף את האפליקציה תוך 3 דק׳) — אותה גרסה עוברת בניסיון הבא בנתיב הרגיל. session של device owner שנכשל באנדרואיד 10/11 —
אותה גרסה עוברת למסלול המסך (לא נתקעים).

**ה-F20 ו-"Parse error when parsing manifest":** זו שורת הלוג של `PackageInstallerActivity` במתקין של אנדרואיד — ממשק האישור לא הצליח לקרוא את
ה-APK שהונח ב-session (ב-ROM של ה-F20; אותו APK מותקן בלי בעיה דרך FileProvider, והמערכת אימתה אותו לפני שהציגה את המסך). session של device
owner לא עובר בממשק הזה בכלל (המערכת מתקינה ישירות), ולכן לא אמור להיתקל בזה; נוסף `setSize` (המקום נשמר מראש) ו-`INSTALL_REASON_POLICY`
לבעלים. המסלול החלופי נשאר.

### 5.2 מה הקופה מדווחת ומה רואים בדשבורד

- **heartbeat** — בלוק `deviceManagement` (`system/DeviceManagement.kt` → `app/services/device_management.py`, נשמר ב-`pos_machines.device_management`):
  `deviceOwner`, `updatePath`, `silentUpdate`, `sdk`, `canRequestInstalls`, `kioskLock` (`full` נעילה מלאה / `pinned` הצמדת אפליקציה / `none`),
  `lockTaskPermitted`, `vendorInstaller`, `permissionsGranted` / `permissionsMissing`, `provisionedBy` (`adb` / `qr`), `ownerReleasedAt/By`,
  `ownerSessionFailed`. גרסה ישנה לא שולחת — "לא ידוע".
- **עמוד המכשיר** — כרטיס "עדכון שקט ובעלות מכשיר": **עדכון שקט: פעיל · <נתיב> / דורש לחיצה**, בעלות מכשיר, אנדרואיד, נעילת קיוסק, הרשאות,
  שחרור בעלות (מתי ומי), "איך מפעילים" ו"הפעל מחדש".
- **"עדכוני גרסה" ← פריסה** — עמודת "עדכון שקט" לכל מכשיר + "איך מפעילים" (`GET /app-releases/rollout`: `deviceOwner`, `silentUpdate`, `updatePath`, `kioskLock`).
- **"איך מפעילים"** — חלון עם שתי לשוניות: פקודת adb לפי סוג מכשיר (עם בדיקות ותנאים, כפתור העתקה) ו-QR למכשיר אחרי איפוס.

### 5.3 הגדרה — adb (מכשיר בלי חשבונות)

2. הפקודה: `adb shell dpm set-device-owner il.co.runnersys.pos/.system.PosDeviceAdmin` → "Success: Device owner set to package il.co.runnersys.pos".
3. בפעימה הבאה (עד דקה) הדשבורד מראה "עדכון שקט: פעיל · בעלות מכשיר".

| סוג מכשיר | אנדרואיד | הערות |
|---|---|---|
| Feitian F20 / Nova 55F | 10 | בלי בעלות מכשיר — לחיצה בכל עדכון. Agamento ושירות ה-FT הם אפליקציות מערכת. |
| קיוסק HIT (RK3568) | 12 | גם בלי בעלות — שקט אחרי אישור "לא מוכרות"; בעלות מוסיפה נעילה מלאה. |
| Kozen P18 | 13 | כמו HIT. |
| SUNMI T2 | 7.1 | אין "לא מוכרות" לפי אפליקציה — בלי בעלות, לחיצה. מכשיר שמנוהל ב-SUNMI MDM — הבעלות תפוסה. |

| Urovo i9100 | 8.1 | DeviceManager של ה-ROM → שקט גם בלי בעלות. |

### 5.4 הגדרה — QR למכשיר אחרי איפוס להגדרות יצרן (Android Enterprise, אנדרואיד 7+)

1. בדשבורד: עמוד המכשיר (או "עדכוני גרסה" ← פריסה) ← "איך מפעילים" ← QR ← "יצירת קוד QR" (`POST /device-management/provisioning-qr`, `machineId` או `shopId`).
   Wi-Fi (לא חובה) נוסף בדפדפן — הסיסמה לא נשלחת לשרת.
2. **איפוס להגדרות יצרן מוחק את כל מה שבמכשיר** — קודם לסגור משמרת, לשדר אשראי ולוודא שהכול הגיע לענן.
3. במסך הפתיחה נוגעים **6 פעמים** באותה נקודה ריקה → סורק QR (באנדרואיד 7–8 ייתכן שקודם יבקש Wi-Fi כדי להוריד את הסורק).
4. המכשיר מוריד את ה-APK מהענן, בודק את חתימתו, מתקין את הקופה כבעלת המכשיר; בסיום הקופה נפתחת **במסך הצימוד** עם כתובת השרת ממולאת.

תוכן הקוד: `PROVISIONING_DEVICE_ADMIN_COMPONENT_NAME` = `il.co.runnersys.pos/.system.PosDeviceAdmin`; `…PACKAGE_DOWNLOAD_LOCATION` =
`<ענן>/api/v1/device-management/provisioning/apk/<טוקן>` — טוקן HMAC קצר (`<release>.<expiry>.<sig>`, 24 שעות כברירת מחדל, 1–72), כי בזמן ההגדרה
אין למכשיר כותרת הרשאה; גרסה שהוצאה משימוש / טוקן מזויף → 404, פג → 410; `…SIGNATURE_CHECKSUM` = SHA-256 של תעודת החתימה (base64url בלי ריפוד),
נקרא בהעלאה מבלוק החתימה v3/v2 (או v1) של ה-APK (`app/services/apk_signing.py`, בלי תלויות; נשמר ב-`app_releases.signing_cert_sha256`);
`PROVISIONING_LEAVE_ALL_SYSTEM_APPS_ENABLED` = true; `PROVISIONING_LOCALE` he_IL; `PROVISIONING_TIME_ZONE` Asia/Jerusalem; `PROVISIONING_ADMIN_EXTRAS_BUNDLE`
= כתובת הענן והסניף. הגרסה: המשויכת למכשיר / לסניף (שיוך מדורג לא נחשב לסניף), אחרת החדשה ביותר (אזהרה). הכתובת הציבורית: `PUBLIC_API_BASE_URL`,
אחרת כתובת הבקשה (https מאחורי Fly). אזהרות בחלון: localhost / http (מכשיר לא יגיע), **debug_key**, not_assigned.

באפליקציה: `GET_PROVISIONING_MODE` (מכשיר מנוהל מלא) ו-`ADMIN_POLICY_COMPLIANCE` (`system/ProvisioningActivities.kt`, רק המערכת יכולה להפעיל —
`BIND_DEVICE_ADMIN`; חובה מאנדרואיד 12 ל-QR), `onProfileProvisioningComplete` ו-`PROVISIONING_SUCCESSFUL` → מסך הצימוד.

### 5.5 מה משתנה במכשיר שבבעלות הקופה

- עדכוני גרסה בלי לחיצה, בכל גרסה.
- כש"נעילת קופה" מופעלת: נעילה מלאה (בלי יציאה במחווה), הקופה כמסך הבית, מסך דולק בטעינה, Agamento ו-QuickSupport ברשימת המותרות.
- **הרשאות בלי חלונות**: הקופה נותנת לעצמה את הרשאות הריצה שמוצהרות ב-manifest בלבד (`OwnerPermissions`: מצלמה, מצב טלפון ומספרי טלפון,
  Bluetooth מאנדרואיד 12; מיקום / התראות רק אם יוצהרו) — אף פעם לא הרשאה שלא מוצהרת.
- **"הפעל מחדש" מהדשבורד** (`POST /machines/{id}/reboot` → `pendingReboot` ב-heartbeat → `DevicePolicyManager.reboot`): לעולם לא באמצע מכירה,
  תשלום, שולחן פתוח, פעולת אשראי, לקוח בקיוסק, התקנה, או כשנגעו במסך ב-2 הדקות האחרונות — אז `deferred` ונשאל שוב בפעימה הבאה; פג אחרי 30 דק׳.
  רק בעלות מכשיר (`409 reboot_needs_device_owner`). אישור `rebooting` נשלח אחרי שהמכשיר עלה מחדש (זמן הפעולה התאפס).

### 5.6 הסרה בלי איפוס — "שחרור בעלות מכשיר"

מסך הטכנאי (קופה: אבחון ← קוד טכנאי בחלון האישור; קיוסק: מסך הטכנאי שכבר מאחורי הקוד) ← "שחרור בעלות מכשיר", עם אזהרה: עדכונים ידרשו שוב
לחיצה (אנדרואיד 11 ומטה), הנעילה המלאה מסתיימת, מסך הבית ו"מסך דולק" חוזרים, ההרשאות חוזרות לניהול אנדרואיד (נשארות מאושרות, לא נעולות).
`clearDeviceOwnerApp` + יציאה מ-lock task; נרשם ביומן ומדווח לענן (`ownerReleasedAt/By`; הענן רושם אזהרה ביומן).

### 5.7 חשוב — מפתח החתימה חייב להיות סופי לפני הגדרת מכשירים

היום, בלי `keystore.properties`, ה-APK נחתם **במפתח ה-debug של מחשב הבנייה** (`CN=Android Debug`; הדשבורד מזהיר "debug_key"). החלפת מפתח
פירושה: כל מכשיר צריך הסרה והתקנה מחדש (= מחיקת הנתונים המקומיים), אנדרואיד לא יתקין עדכון במפתח אחר, וה-QR (שבודק את החתימה) לא יעבוד.
**מכשיר שבבעלות הקופה צריך קודם "שחרור בעלות מכשיר"** — אחרת אי אפשר להסיר את האפליקציה בלי איפוס להגדרות יצרן. לכן: לקבוע מפתח שחרור
קבוע (keystore מגובה), לבנות ממנו, ורק אז להגדיר בעלות מכשיר.

- **MDM / Android Enterprise** (Esper, Hexnode, Scalefusion, Knox וכו׳) — אותו כוח בקנה מידה; אז ה-MDM הוא בעל המכשיר, והאפליקציה שלנו מתעדכנת דרכו.
- התנהגות האנדרואיד מול הענן לא השתנתה: הבקשה בלי `platform` = אנדרואיד; כל המפתחות הקודמים בתשובה נשארו.

## 8. מסכי קיוסק מהענן — אנדרואיד בלי APK חדש ("אותו APK עם עדכון פנימי")

הבעלים (07.10.2026): "אני לא רוצה לבקש אישור מהאנדרואיד, בעצם אותו APK עם עדכון פנימי" — אושר כחלק ב׳: מסכי הלקוח של קיוסק
אנדרואיד יכולים לרוץ מ**חבילת מסכים (web bundle)** שמתעדכנת מהענן **בתוך אותו APK** — מסכים, עיצובים וזרימות חדשים מגיעים לקיוסקים
בלי התקנת APK, בלי אישור על המסך ובלי Play.

### 8.1 רנדרר אחד, שלושה מארחים

| מארח | מה מריץ את המסכים | הגשר |
|---|---|---|
| Windows (Electron) | `kiosk-desktop/src/renderer` | `window.kiosk` מה-preload (IPC לשירות המקומי) |
| דפדפן | `/k` בדשבורד | הגשר של הדפדפן |
| **אנדרואיד (WebView)** | **אותם מסכים**, בנויים כחבילה סטטית (`vite.android.config.mts`) | `kiosk-desktop/src/renderer/bridges/android.ts` ↔ `window.R2MAndroid` (`ui/kiosk/web/KioskWebSession.kt`) |

המסכים עצמם (`client/src/kiosk-shared`, `kiosk-desktop/src/renderer/kiosk`) לא יודעים באיזה מארח הם רצים: הגשר לאנדרואיד מממש את אותו
`KioskBridge` / `ShellBridge` (`shared/bridge.ts`, `shared/roles.ts`) מעל השירותים ה-native של הקיוסק.

**ה-native נשאר native:** תשלום (Nayax LAN, Agamento — `CheckoutViewModel` של הקופה), מסמכים, מספור ו-Z, הדפסה (בון, קבלה, פתק
איסוף — `KioskBonService`), KDS, סורק (מקלדת-סורק וראש סריקה — `KioskScanner`/`ScanRouter`, הקודים נמסרים למסכים), תקינות
המכשיר (סוללה, באנרים), סנכרון ומדיה, ניהול הקיוסק (לחיצה ארוכה בפינה הימנית העליונה + קוד מנהל) ומסך הטכנאי (6 נגיעות בפינה
השמאלית העליונה) — כשכבה native מעל ה-WebView.

**מה עובר בגשר (bridgeApi 1):** `bootstrap` (תצוגת הקיוסק: התצורה מהענן עם המדיה המקומית, הקטלוג כפי שהקיוסק מוכר — תפריט פעיל,
מוסתרים, אזל — עם קבוצות התוספות וההערות המהירות מהתפריט, מצב השהיה/מסופון/אינטרנט/אשראי חסום), `startPayment` (הסל של המסכים
← `Cart` של הקופה — `KioskWebCart.kt` — ← `KioskViewModel.webCheckout` ← אותו `startPayment` של המסכים המובנים: בדיקת הסל מול
הענן, משמרת, הזמנה, מסופון, מסמכים, בון, KDS), `cancelPayment`, `receiptChoice`, `helpRequest` (התראה לקופות), `reportFlow` (הזרימה
של המסכים משתקפת בזרימה ה-native: סגירה אוטומטית / Z, סטטוס בענן, שערי הצוות), `funnel` (ביצועי קיוסקים — לאותו מאגר), ומהאפליקציה
למסכים: `view` (כל שינוי), `pay` (התקדמות התשלום), `scan` (קוד מהסורק), `shell`. כל השמות נעוצים ב-fixture משותף:
`kiosk-desktop/test/fixtures/android_bridge_api.json` = `pos-android/app/src/test/resources/kiosk_web_bridge_api.json` (אותם בייטים).

**כלל המחיר:** לעולם לא יותר ממה שהלקוח ראה. מחיר יחידה גבוה ממה שהמסך הציג (או מוצר שירד) — "הסל השתנה" עם הסכום החדש, לפני
כל חיוב. נמוך יותר (מבצע, בחירה חינם) — מחויב כפי שהוא, ומסך התשלום מציג את הסכום בפועל.

### 8.2 מה מתעדכן בלי APK — ומה עדיין צריך APK

| בלי APK (חבילת מסכים) | צריך APK |
|---|---|
| מסכי הלקוח: מראה, סגנונות, פריסות (layouts), אנימציות, טקסטים מובנים, מסכים חדשים וזרימות חדשות בתוך מה שהגשר יודע | כל דבר native: תשלום ומסופונים, מסמכים ומספור, Z, הדפסה, KDS, סורק, סנכרון, ניהול וטכנאי |
| תיקוני באגים במסכים | יכולת חדשה בגשר (קריאה / אירוע / שדה שהמסכים צריכים מה-native) — `bridgeApi` עולה (§8.6) |
| שינוי התנהגות שנקבעת בתצורה ממילא (גם בלי חבילה — מהענן) | שינוי במתג, ב-watchdog, בטעינת החבילות עצמה |

### 8.3 המתג — לכל מכשיר / סניף, ברירת מחדל: המסכים המובנים

- `general.renderer` בתצורת הקיוסק: `"native"` (ברירת מחדל — הקיוסק Compose של היום) או `"web"`. שכבות כרגיל: חברה ← סניף ← מכשיר,
  כך שהבעלים מעביר סניף שלם או מכשיר אחד. בדשבורד: קיוסקים ← הגדרות ← כללי ← "מנוע תצוגה בקיוסק אנדרואיד".
- הקיוסק מציג web רק אם (`KioskWebRules.pick`): הוגדר `"web"`, יש חבילה שה-APK מדבר את ה-`bridgeApi` שלה, ה-WebView של המכשיר
  לפחות `minChrome` של החבילה (היום Chrome 111 — Tailwind 4), והחבילה לא נכשלה במכשיר הזה ב-APK הזה. אחרת — המסכים המובנים,
  והסיבה מדווחת לענן.
- סדר המועמדות: החבילה הפעילה ← הקודמת (rollback) ← החבילה שבתוך ה-APK.

### 8.4 שומר (watchdog) וחזרה למסכים המובנים

| מה | תגובה (`fallbackReason`) |
|---|---|
| המסכים לא דיווחו "מוכן" (המסך הראשון צויר) תוך 25 שנ׳ | `ready_timeout` |
| תהליך הרינדור של ה-WebView קרס / נהרג (`onRenderProcessGone`) | `render_gone` |
| שגיאה שהשאירה מסך ריק, או 5 שגיאות בדקה | `js_errors` |
| שגיאת טעינה של הדף הראשי | `load_error` |
| WebView ישן מדי / לא ידוע | `webview_old` |
| אין חבילה / ה-APK לא מדבר את ה-bridgeApi | `no_bundle` / `bridge_api` |

כשל מסמן את החבילה כ"פגומה" **במכשיר הזה וב-APK הזה** והקיוסק עובר מיד למועמדת הבאה (הקודמת, ואז של ה-APK), ובסוף למסכים
המובנים — באמצע הפעולה, בלי לחכות. הענן מקבל דיווח (`POST /sync/{m}/kiosk-web/status`, וסטטוס `failed` לגרסה). הסימון נמחק כשמותקן
APK אחר, או כשהבעלים מעביר את המתג ל-native ובחזרה ל-web (ניסיון חוזר מכוון).

### 8.5 החבילה — בנייה, העלאה, שיוך, הורדה, החלפה

- **בנייה:** `cd kiosk-desktop && npm run build:android-bundle` → `dist/kiosk-web-bundle-<גרסה>.zip`. בתוכה `manifest.json`:
  `kind: "r2m-kiosk-web"`, `version` (זמן הבנייה UTC, `YYYY.MM.DD-HHMM`), `versionCode` (דקות מ-2025-01-01, רק עולה), `bridgeApi`,
  `minChrome`, `entry`, `files` — לכל קובץ SHA-256 וגודל. הזיפ דטרמיניסטי (אותם קבצים → אותם בייטים).
- **העלאה:** "עדכוני גרסה" ← פלטפורמה **"מסכי קיוסק (ווב)"** (`kiosk_web`) ← הזיפ (הגרסה נקראת מהמניפסט; הענן בודק כל קובץ מול
  המניפסט ומסרב לנתיב לא בטוח / קובץ חסר / עודף / hash שגוי — `422 invalid_bundle`), או מסקריפט:
  `R2M_ADMIN_TOKEN=… npm run publish:android-bundle -- --server https://… [--assign shop:<id>] [--percent 20] [--rollback]`.
- **שיוך:** בדיוק כמו גרסאות (מכשיר ← נקודת מכירה ← סניף ← חברה ← ארגון, החדש ברמה, אחוז פריסה). **חזרה לחבילה קודמת מותרת**
  (`allowDowngrade`) — אין כאן מגבלת versionCode של אנדרואיד. "התקנה אוטומטית" וחלון ההתקנה לא חלים על חבילות: חבילה תמיד
  מתחלפת לבד — ורק כשהקיוסק פנוי.
- **במכשיר** (`KioskWebController`, כל עוד הקיוסק על המסך: 20 שנ׳ אחרי עלייה ואז כל 15 דק׳):
  `GET /sync/{m}/app-update?platform=kiosk_web&versionCode=&versionName=` → הורדה ברקע לקובץ זמני → SHA-256 של הזיפ מול הענן →
  פריסה לתיקייה זמנית (בלי "zip slip") → בדיקת **כל** קובץ מול המניפסט (גודל, SHA-256, אין קבצים עודפים) → שינוי שם לתיקייה
  `filesDir/kiosk-web/b/<…>` → **ממתינה**. ההחלפה רק **כשהקיוסק פנוי**: הזרימה ה-native במנוחה (פתיחה / סגור / מושהה), המסכים
  מדווחים idle, בלי סל ובלי תשלום. החבילה הקודמת נשמרת (rollback). חבילה שדורשת `bridgeApi` שה-APK לא מדבר — `declined`, לפני ההורדה.
  דיווחים: `downloading` → `downloaded` → `installed` (= המסכים שלה צוירו) / `failed` / `declined`.
- **חבילת גיבוי בתוך ה-APK:** `assets/kiosk-web/bundle.zip`, מהתיקייה `pos-android/app/kiosk-web-bundle/` (srcDir ב-`build.gradle.kts`),
  שנכתבת ע"י `npm run build:android-bundle -- --apk ../../pos-android`. בניית האנדרואיד **לא מריצה npm**: אין זיפ — אין חבילת גיבוי
  (קיוסק שהוגדר web נשאר במסכים המובנים עד שהענן שולח חבילה, `no_bundle`). החבילה של ה-APK נפרסת פעם אחת לכל APK.

### 8.6 bridgeApi — גרסאות הגשר

- `bridgeApi` הוא החוזה בין המסכים לאפליקציה (שמות הקריאות, האירועים והשדות). החבילה מצהירה מה היא צריכה; ה-APK מדבר טווח
  (`KioskWebProtocol.MIN_BRIDGE_API..BRIDGE_API`, היום 1..1).
- שינוי **מוסיף** (שדה אופציונלי חדש, אירוע שחבילה ישנה מתעלמת ממנו) — בלי העלאה. חבילה שצריכה יכולת native חדשה — מעלים את
  `ANDROID_BRIDGE_API` (`kiosk-desktop/src/renderer/bridges/androidWire.ts`), משחררים קודם APK שמדבר אותו, ורק אחריו את החבילה.
  APK חדש ממשיך לענות לחבילות ישנות (טווח), כדי שהחזרה לחבילה קודמת תמיד תעבוד.
- נבדק בשלושה מקומות: הענן מחזיר `bridgeApi` בהצעה (המכשיר מסרב בלי להוריד), המכשיר בודק את המניפסט אחרי הפריסה, והחבילה בודקת
  את `R2MAndroid.bridgeApi()` בעלייה.

### 8.7 מה המכשיר מדווח ומה רואים בדשבורד

`POST /sync/{m}/kiosk-web/status` — `renderer` (מה על המסך עכשיו: `native` / `web`), `configured` (מה הענן ביקש), `bundleVersion`,
`bundleVersionCode`, `bundleSource` (`bundled` / `downloaded`), `previousVersion`, `pendingVersion`, `apkBridgeApi`, `fallbackReason`,
`message`. בדשבורד ("עדכוני גרסה" ← "מסכי קיוסק (ווב)" ← פריסה): לכל קיוסק — החבילה שהוא מריץ, מנוע התצוגה עכשיו ומה הוגדר, סיבת
חזרה למסכים המובנים בעברית, החבילה הממתינה, ומי מפגר.

### 8.8 נעילת ה-WebView

רק המקור `https://appassets.androidplatform.net` (החבילה, `/media/` של הקיוסק, `/pimg/` של תמונות המוצרים — `KioskWebAssets.kt`,
נתיבים שלא יוצאים מהתיקייה), שום כתובת אחרת (גם לא ניווט/הפניה), בלי גישה לקבצים / content, בלי mixed content, בלי חלונות,
הרשאות או מיקום, CSP קשיח בחבילה (`android.html`: `default-src 'self'`), ממשק ה-JS עונה רק לדף שלנו, ניפוי באגים רק ב-debug,
מטמון כבוי (כל החבילות באותו מקור), ו-R8 שומר את מתודות ה-`@JavascriptInterface`. מקלדת-סורק לא מגיעה למסכים כמקשים — הקוד נמסר כאירוע.

### 8.9 פערים מול המסכים המובנים (שלב 2) — מה הולך לאיבוד היום כשעוברים ל-web

- **ארוחות (משבצות בתפריט):** המסכים לא ממלאים משבצות — ארוחות לא מוצגות בקטלוג ה-web באנדרואיד.
- **"איך תרצו לשלם?"** — שובר / שובר מראש / "מזומן בקופה" (`KioskPayMethodModel`): ב-web רק אשראי (גם ב-Windows היום).
- **תוספות עם כמות לכל אפשרות (`allowQuantity`, `maxQty`), "מעט/הרבה/בצד" (`allowPre`), בחירות חינם (`freeCount`)** — המסכים לא
  מציגים; בחירה חינם מחויבת נכון אבל המסך מציג את המחיר המלא.
- **מבצעים** — מחושבים בתשלום (הלקוח לא משלם יותר), אבל לא מוצגים בסל של המסכים.
- **הגדלת מכירה:** כללי זמן/ימים, "חובה/רשות" לפי שלב וסטטיסטיקת הצעות (`UpsellEngine`, `upsellStats`) — ב-web גרסה פשוטה.
- **מגבלות הזמנה למוצר / refills (`productLimits`)**, **הערות "חשוב"** והצהרת אלרגיות בגיליון המנה.
- **פרטים אחרי התשלום** (`detailsStep: after_pay`): השם שנאסף במסכים אחרי התשלום לא מגיע לבון.
- **מצב בקשת העזרה** ("קראנו לצוות" / "הצוות בדרך" / "פנו לקופה") — ב-web הודעה קצרה בלבד; **"איך מזמינים?"** (`helpText`).
- **חיפוש בקטלוג** (`searchEnabled`), **הודעת "אין אינטרנט" ללקוח** (`offlineNotice`), **צליל אין אינטרנט** מהמסכים.
- **החלפת שפה** עם הטקסטים המובנים של האנדרואיד (en / ar) — ב-web לפי מה שהמסכים המשותפים תומכים.
- **כפתור "חזרה" של המערכת** לא מועבר למסכים (במסכים יש חזרה משלהם); **סריקות במסך הטכנאי** ("סרוק לבדיקה") לא מראות את תוצאת ה-web.
- תמונות מוצר בגדלים מוקטנים (WebP ‏480/960 כמו ב-Windows) — היום הקובץ המקורי.
